# P8: Firefox and WebKit

Date: 2026-11-05. Record: `P8-S-2026-11-05.json`.

Verdict: **GO for Firefox.** Safari is not measured: the WebKit available on Windows runs everything but browser storage, which that port does not have.

## Question

The decision is Chromium first, with Firefox and Safari functional (investigation, Decisions). Do the browser node's features work in the other two engines with the same results, and where they do not, what is the reason?

## Set-up

- **Engines:** Playwright 1.65's own builds: Firefox 159, and WebKit 27.2 (the engine Safari uses, built for Windows; its user agent says Safari, but it is not Safari). Chrome 156 runs P0 alone, as the reference picture.
- **Features:** every POC that has an S fixture, run by its own handler in the other engine, each with its own pass rule:

| Feature | POC | Passes when |
|---|---|---|
| product rendering modules; node-fed and browser-fed canvases identical | P0 | the canvases are identical, only page-side shims, HD byte order understood |
| OME-TIFF tiles from a picked file | P1 | 100/100 tiles byte-identical to the node's HD tiles |
| flat mask → label pyramid in OPFS | P2b | 200/200 derived tiles identical to Python's |
| flat image → pyramid in OPFS (zlib strips, tiles) | P7 | every compared tile identical to Python's |
| CSV → column store; the five table questions | P3 | all_cells, columns, describe, nearest, ROI and gates identical |
| h5ad and SpatialData | P4 | every read identical, apart from the known lzf-string gap |

- **The picture across engines:** P0's browser-fed canvas at three views (home, mid zoom, native), as a 16 × 10 grid of mean luminance, against Chrome's. Engines rasterise the same tiles slightly differently, so byte identity across engines is not expected.

## Results (Measured)

| Feature | Firefox 159 | WebKit 27.2 (Windows) |
|---|---|---|
| P0 rendering | pass | pass |
| P1 tiles | pass | pass |
| P2b mask pyramid in OPFS | pass | **fail**: `NotSupportedError: Backend does not support this operation` |
| P7 image pyramid in OPFS | pass | **fail**: the same |
| P3 CSV column store | pass | **fail**: `UnknownError` from OPFS |
| P4 h5ad, SpatialData | pass | pass |
| Picture vs Chrome, worst grid cell | 0.4 of 255 levels | 0.1 of 255 levels |

- **Firefox does everything Chrome does here, with the same answers.** That covers OPFS sync access handles, nested workers, `CompressionStream`, `webkitdirectory` folders and h5wasm's IIFE build. Its pictures are within 0.4 of a level of Chrome's in every grid cell.
- **The WebKit failures are the port, not the engine's features.** Every failure is the origin private file system refusing an operation, and WebKit on Windows has no backend for it. Safari on macOS has OPFS, sync access handles in workers included (Platform). So these three rows say nothing about Safari either way.
- **Findings made on the way, both fixed in the POC:**
  - a P2b fixture that was already a pyramid (exemplar-001's mask has two SubIFDs) was refused by the new builder's "flat only" check; the builder now rebuilds from level 0 and records the layout;
  - Firefox's `Error.stack` leaves out the message, so workers now send both.

The plan's "M opens on Firefox" was not run: M's files are tens of GB, and the S features are the same code.

## Open

- **Safari on a Mac:** the same handler with Playwright's WebKit on macOS, which has OPFS (`node bench/run.mjs --poc P8 --fixture S --params '{"engines":["webkit"]}'` on the M2 laptop).
- **Firefox's 10 GiB quota** (a real limit, unlike Chrome's report; investigation §2.4) is not reached by S.
