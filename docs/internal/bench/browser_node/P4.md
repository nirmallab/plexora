# P4: AnnData and SpatialData in the browser

Date: 2026-11-05. Records: `P4-S-2026-11-05.json` and `P4-L-2026-11-05.json`.

Verdict: **PARTIAL.** Every read the browser can make returns Python's bytes. The one thing it cannot read is an lzf-compressed string array. But h5wasm takes 2–13× h5py's time, against a 2× hypothesis.

## Question

Can the browser read the AnnData and SpatialData files Plexora's Python adapter reads, with the same answers, in bounded time? Is the set it cannot read small, and does each gap have a named way round it?

## Set-up

- **.h5ad:** `workers/h5Worker.js` runs h5wasm 0.10.3 (libhdf5 in wasm) in a worker. The picked `File` is mounted through Emscripten's WORKERFS, so libhdf5 reads only the bytes it asks for. h5wasm-plugins 0.3.0 supplies lzf, zstd, blosc, lz4 and bitshuffle; gzip is built in.
  - The reads are the adapter's: obs names; a numeric obs column (`X_centroid`); a categorical one (codes and categories); `obsm["spatial"]`; var names; a 64 MB row block of X (the adapter's block size); one X column; and all of X in row blocks as columns, the pass that fills a column store.
  - A string array is read whether it is a dataset or, as anndata writes since 0.11, a `nullable-string-array` group.
  - Each read runs 3 times and the median is kept, as on the Python side. Each read is its own message, so one failure cannot hide the rest. A filter that aborts takes its wasm instance down with it, and the page starts a new worker for the next read.
- **SpatialData:** zarrita 0.7.5 over the picked folder (`<input webkitdirectory>`) reads the zarr v3 store spatialdata 0.8 writes: the table's obs, obsm and X (sharded, zstd); the image's multiscales and a chunk; a label region. hyparquet 1.31.5 reads the shapes (GeoParquet, WKB) and the points. DuckDB-Wasm reads the same two files beside it, for comparison.
- **Reference:** `bench/truth_p4.py` makes the same reads with h5py, zarr-python and pyarrow (median of 3). It hashes every answer in the layout the page hashes: float64, float32 or int8 bytes; strings joined with `\n`. The driver compares the hashes.
- **Fixtures** (`bench/p4_fixtures.py`):
  - L: Orion CRC02's 1,260,592 cells × 90 float32 features (its 20 markers and morphology, then synthetic log-normal ones), written by anndata 0.13 as {dense, CSR} × {none, gzip, lzf}: 0.23–0.56 GB each. CSR keeps the values above each feature's 70th percentile.
  - S: the same from exemplar-001 (11,201 cells).
  - SpatialData: a 12,000 × 12,000 crop of LSP11385 (2 channels, three scales), its label crop (31,370 cells), circles at their centroids, 50,000 points and a table annotating the labels (L); a 6001 × 7003 crop (S).

## Results (Measured)

**Identity.** At L, 53 of 59 reads are byte-identical to Python's; at S, 47 of 53. Every one of the 6 that are not is a string array in an lzf file:

| | none | gzip | lzf |
|---|---|---|---|
| obs names, var names, categorical (strings) | identical | identical | **unsupported**: the lzf plugin aborts (`memory access out of bounds`; under Node, `undefined symbol '__errno_location'`) |
| numeric obs, obsm, X row block, X column, all of X | identical | identical | identical |

- Dense and CSR X read alike. anndata 0.13's `nullable-string-array` index groups read like plain string datasets.
- **SpatialData:** all 8 reads match zarr-python and pyarrow. That covers the sharded zstd table, the image multiscales and a chunk, the label region, the GeoParquet shapes as WKB bytes and as GeoJSON, and the points. DuckDB's two reads match too.

**Time at L** (1,260,592 × 90; the median of 3, browser against Python, ms):

| Read | dense, none | dense, gzip | CSR, none | CSR, gzip | dense, lzf |
|---|---|---|---|---|---|
| obs names (1.26 M strings) | 1187 / 383 | 1380 / 407 | 1380 / 378 | 1703 / 416 | — |
| a numeric obs column | 15 / 5 | 243 / 43 | 16 / 6 | 230 / 42 | 187 / 18 |
| obsm["spatial"] | 29 / 10 | 599 / 88 | 31 / 10 | 533 / 83 | 463 / 34 |
| X, a 64 MB row block | 105 / 33 | 1130 / 299 | 558 / 59 | 749 / 158 | 904 / 83 |
| X, one column alone | **5636 / 101** | 181 / 40 | 3609 / 271 | 4289 / 943 | 120 / 12 |
| X, all of it as columns | 919 / 525 | 8636 / 2262 | 3789 / 519 | 4809 / 1226 | 6257 / 831 |

- **h5wasm is 2–13× h5py** for the reads the adapter makes. That is libhdf5 and its filters compiled to wasm, plus WORKERFS turning each read into a synchronous File slice. gzip and lzf data cost the most (zlib and lzf in wasm).
- **One read is pathological:** a single column of an uncompressed, unchunked dense X takes 5.6 s, 56× h5py. libhdf5 reads a strided column as one tiny read per row, and each read through WORKERFS is a call into the browser. h5py does the same reads against the OS page cache.
- **What the browser node should do instead** is what the adapter already does for narrow tables: read X once in row blocks into the column store. That costs 0.9–8.6 s at 1.26 M × 90, against 0.5–2.3 s for h5py.
- **SpatialData reads** take 2–12× zarr-python's time, at tens of ms; the 150 ms obs read is 31,370 index strings.
- **Parquet:** hyparquet reads the shapes in 16 ms and the points in 17 ms, with **no network**. DuckDB-Wasm's first `read_parquet` takes 0.59 s, because it fetches `https://extensions.duckdb.org/v1.5.4/wasm_eh/parquet.duckdb_extension.wasm`. That is the only request either fixture made outside the page's own origin.
- **Memory:** the renderer peaked at 3.19 GB over the whole matrix. One read of all of X holds the full 454 MB column-major copy, plus h5wasm's heap and its 64 MB blocks.

## Thresholds

| Threshold | Bound | Measured (L) | |
|---|---|---|---|
| obs, obsm, X row block and X column read and identical, none and gzip | all | 24/24 | pass |
| slowest of those vs h5py (reads h5py takes ≥ 5 ms) | ≤ 2× | 55.7× (one dense column alone); 2.6–13.3× otherwise | **fail** |
| SpatialData reads identical | all | 11/11 | pass |
| every unsupported read has a named conversion | all | 6/6: lzf strings → re-save with gzip, or read on a node | pass |
| STOP: obs or obsm unreadable | none | none | |

## Consequence

- **h5ad works in the browser, slowly.** Correctness is not the issue; speed is. The design copies an h5ad's obs, obsm and X into the OPFS column store on first open, once: about 1–9 s at 1.26 M × 90, against seconds for a CSV of the same size. After that it is read like any other table. A node stays the better home for large h5ad files.
- **lzf:** an h5ad written with `compression="lzf"` has unreadable strings in the browser until h5wasm-plugins' lzf filter is fixed. The page says so and offers the node.
- **Parquet goes to hyparquet**, not DuckDB (investigation §3).
