# P0: the rendering layer from a static origin

Date: 2026-11-05. Records: `P0-S-2026-11-05.json`, `P0-M-2026-11-05.json` and `p0_audit-2026-11-05.json`. Verdict: **GO** on both fixtures.

Tags as in `docs/internal/BROWSER_NATIVE_INVESTIGATION.md`: **Measured** comes from these records, **Design** is read from the source, **Proposed** is not done here.

## Question

Can the product's rendering modules run, unmodified, on a page served from a plain static origin with no Flask, no Jinja and no `window.flaskVariables`? The modules are `glInit.js`, `tileColorize.js`, `tileDecode.js`, `tileFetch.js`, `labelTile.js`, `labelGpu.js`, the shaders and `workers/tileDecoder.js`. And do they draw the same picture whether the pixels come from a Python node or from the browser reading the file itself?

## Set-up

- `tools/poc_browser_node/page/index.html` loads the product client from the checkout through `../repo/plexora/client/...`, in `base.html`'s order: `passVariablesToFrontend.js`, the vendor bundle, `displayCurve.js`, `layerStack.js`, then the six rendering modules.
- `PLEXORA_BASE_URL` is set at runtime from `location`, so `plexoraUrl()` resolves the shader URLs from wherever the page is served.
- `page/src/viewer.js` builds a minimal OpenSeadragon viewer from those modules. It supplies ImageViewer's few lookups (`indexOfTexture`, `selectTexture`, `selectCenterProps` with no cells) and uses the product's OSD options.
- **Two arms draw the same channels with the same windows:**
  - **node:** OSD's own XHR to `plexora node serve`'s HD tiles, decoded by the product's tile-loaded handler and its worker. This is today's direct route.
  - **browser:** geotiff.js workers over the picked `File`, delivered the way `tileFetch.js`'s `deliver` hands a decoded plane to a tile.
- **Fixtures:** S is `flat.ome.tif` (3 × 2048², deflate, 256 tiles). M is LSP11385 (40 channels × 52923 × 45381, 7 levels, deflate with predictor 2, 66.7 GB).
- **Views** are home, mid zoom and native resolution. The zoomed views are centred on tissue, found from the coarsest level.

## Results (Measured)

**The modules load unmodified.**
- Every rendering global is defined.
- One page-side shim is needed: `toFloatColor`, a one-line function declared in `imageViewer.js` and called by `tileColorize.js`.
- lodash's `_` is a global on the static page too.
- `datasource` and `flaskVariables` are absent; nothing in the rendering set reads them.

**The pictures are identical.** Each view is 648,000 pixels. (The second round's records, with the fixed shader, have a few hundred more non-black pixels per view than the first round's: 460,072 → 462,680 at S home, for instance. Pixels the old rebuild drew just below a window's floor now light up. The two feeds still agree pixel for pixel.)

**Byte order.**
- The node's HD tile is a 16-bit grey PNG with big-endian samples: 262,144 of 262,144 samples match.
- geotiff.js returns native little-endian.
- The browser node swaps the bytes before delivery (about 2 ms a tile in the worker). The shader and the upload code are untouched.

**`frag.glsl:504` rebuilt the 16-bit value as `r * 255 + g`; fixed since.** The exact value is `r * 256 + g`. A ramp was drawn through the product's own renderer and read back. The first round found:

| Window | Values | Worst error (8-bit display levels) | Mean error |
|---|---|---|---|
| [0, 1] (whole range) | k · 257, k = 0..255 | 1 | −0.5 |
| [0.50, 0.55] (bright, tight) | 32768 … 36044 | **11** | **−10.2** |

The error grows with the high byte and shrinks with the window. A bright channel levelled tightly drew about 4 % darker than its window said, and a saturated pixel in a window at the top of the range nearly black. It was an existing product bug, independent of the browser mode (investigation §9, question 11). It is fixed on main (9a2b1912: `r * uint(256)`), with `tests/test_hd_u16_shader.py`, which draws through the same renderer in Chromium and fails on the old line. **The second round's records show the fixed shader: worst error 0 in both windows.**

The rendering set is almost clean:
- `glInit.js` makes two `plexoraUrl` calls, for the shader URLs, which already resolve against a runtime base.
- `tileColorize.js` uses `toFloatColor` and `PlexoraLayerStack`; the latter only for a registered layer.

## Seams found (Design)

1. **The tile-source helpers are private to the webpack bundle.** These are `toTileLevels`, `toMagnifiedBounds`, `getTileKey` and the rest in `viewerManager.js`. The proof of concept copies them (`page/src/tileSource.js`). A static build should export them.
2. **`toFloatColor` lives in `imageViewer.js`.** It belongs with `tileColorize.js`.
3. **OpenSeadragon infers transparency from a tile URL ending in `.png`** (`TileSource.hasTransparency`), and clears the tile rectangle before drawing it. A browser-node tile source whose address had no `.png` composited differently: 451 pixels differed, by up to 25 levels. Any non-HTTP tile source must keep the product's `.png` addresses or override `hasTransparency`. The pictures above are identical with that rule in place.
4. **Order.** The tile-loaded and tile-drawing handlers must be registered before the first item is added, as the product does by opening the viewer before adding channels. Otherwise early tiles are never decoded.

## Consequence

No rendering code has to change for a static build. The Phase 0 seam is the four items above plus the template work (investigation §6.3).
