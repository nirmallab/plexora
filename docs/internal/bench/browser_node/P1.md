# P1: a local OME-TIFF read by the browser node

Date: 2026-11-05. Records:
- `P1-M-2026-11-05.json`: tiles, decoders, identity, auto-level;
- `P1V-M-2026-11-05.json`: the viewer arms, ABBA;
- `P1R-none-2026-11-05.json`: the same reader over HTTP range requests against a bucket.

Verdict: **GO**.

## Question

Can geotiff.js workers reading a local `File` serve 1024² uint16 tiles fast enough for the product's renderer, byte-identical to the Python HD path? Can they open a large multichannel OME-TIFF in seconds? This is the make-or-break item for "no local Python" (investigation §9, question 1).

## Set-up

- **Fixture M:** LSP11385.ome.tif. 66.7 GB, BigTIFF, 40 channels × 52923 × 45381 uint16, 7 levels as SubIFDs, 1024² tiles, deflate with predictor 2.
- **Machine:** Windows 11, i9-12900K (24 threads), 128 GB, RTX 3080, NVMe. Chrome 156 headless on the GPU (ANGLE/D3D11), with the frame-rate limit off, so frame intervals are frame cost. Whole-machine CPU was 10–25 % busy before each run (the user's own browser and services), recorded per record.
- **The reader** is `page/src/lib/tiffReader.js`.
  - Main IFDs are parsed at open; a level's SubIFD is parsed on first use.
  - Tile offsets are loaded in one read per level.
  - Tiles are read with `readRasters` over the Plexora 1024 grid, clipped at the edges as `read_tile` clips them.
  - Deflate goes through the browser's `DecompressionStream`; pako is the alternative.
  - Output is swapped to big-endian for the existing shader.
- **The Python reference** is `plexora node serve` on the same file. Its `?q=hd` tiles are what the desktop primary forwards unchanged.

## Results (Measured)

**Open** (main IFDs, OME-XML channel names, level sizes):

| Workers | 1 | 2 | 4 | 8 | 24 |
|---|---|---|---|---|---|
| open, all workers (ms) | 60 | 82 | 144 | 214 | 563 |

One worker reads 49 slices (193 KB) to open the 40-channel file. tifffile takes about 1 s locally (investigation §5.2). The cold header walk the investigation feared is not a cost: geotiff.js parses lazily.

**Tiles** (100 random tiles, one at a time; then 200 with every worker busy):

|---|---|---|---|---|
| 1 | 19.3 / 28.5 | 2.9 | 3.8 | 56 |
| 2 | 19.0 / 27.0 | 2.8 | 3.2 | 108 |
| 4 | 20.5 / 35.5 | 3.0 | 3.5 | 180 |
| 8 | 18.9 / 25.6 | 2.5 | 3.3 | 275 |

(The second round's record. The first round's, with inflate fed through a Blob, read 21.1 / 31.2 ms at 4 workers, inflate 3.8–4.8 ms, and 48–376 tiles/s.)

- **Inflate:** native `DecompressionStream` is 4.4 ms p50 (8.8 p95). pako is 7.9 ms (19.5). Native is the choice.
  - **Second round:** the bytes are now written straight into the stream, not wrapped in a Blob first: 3.1 ms p50 (6.2 p95), against 4.1 ms (8.7) through a Blob and 7.7 ms (21.2) for pako, on the same 50 tiles. The product's own HD worker (`workers/tileDecoder.js`) uses the Blob form, so it could save about 1 ms of decode a tile; a tile's total here is 21 ms either way, so it is a note, not a change. At gigabyte scale the Blob form fails outright (P7).
- **The rest of a tile** (about 12 ms) is geotiff.js's predictor and window copy in JavaScript plus the byte swap: room to optimise, not needed for GO.

(Second-round record; the first round's figures were within a few per cent.)

- **Every tour step reached full in both arms**: 11 steps at mixed zoom, seeded.
- **The browser node reaches full 2.3–2.9× sooner**: step-time ratios 0.34 to 0.44.
- **Panning:** both arms stay well inside the 60 Hz budget with no long tasks.
- **Memory:** the JS heap is the same in both arms. It is OpenSeadragon's tile cache, and it passes 2 GB at 15 channels in either arm.

**A bucket, no node** (`P1R`). The same reader read Orion CRC02 over HTTP range requests straight from `s3://lin-2023-orion-crc` (CORS `*`): 73.4 GB, 19 channels × 48460 × 58709, 7 levels. The browser was fresh and cold.
- **Open: 7.0 s** (6.9 s in the first round). That is 28 sequential range reads of 107 KB; the IFD chain is one round trip per IFD.
- **Tiles:** p50 359 ms, p95 585 ms, almost all network (3 reads a tile).
- **For comparison:** tifffile's cold header read of the same files is 21–25 s, or 6.5–10 s with SubIFDs batched (repository notes, Measured 2026-10-29).

## Limits of this run

- **The Python arm is a local node, not the desktop primary.** Tiles are the same bytes from the same code (`encode_tile_array`), and the desktop's own local path adds Flask routing on top. Both arms are read through the same static-page viewer. The product page itself was not timed.
- **M only.** S and the 303 GB L were not timed. Codec coverage here is deflate with predictor 2 and plain deflate; LZW, zstd and JPEG come from geotiff.js's own decoders and are untested.
- **Chrome only.** Firefox and Safari are P8.
