# P7: a flat image made into a pyramid in the browser, and what survives a relaunch

Date: 2026-11-05. Records: `P7-S-2026-11-05.json`, `P7-M-2026-11-05.json`, and `P7-M-2026-11-05-w8.json` (the strips layout with 8 workers).

Verdict: **GO** on S and M.

## Question

A multichannel image is often written flat: one level per channel, no pyramid. Plexora's Python modes convert such a file once (`server/utils/image_pyramid.py`, offered for any flat image wider than 4096 px). Can the browser do the same conversion, into OPFS, with Python's numbers exactly, in comparable time, without hurting the page? And is the result still there, and quick to reopen, after the browser is relaunched?

The plan's P7 also asked about the OPFS quota. That answer is in "Storage" below.

## Set-up

- **The builder** (`page/src/workers/pyramidWorker.js` with `pyramidBandWorker.js`) is the one P2b uses for masks, with Python's image arithmetic (`page/src/lib/reduce.js`, a transcription of `image_pyramid.reduce2`):
  - a 2 × 2 mean, an odd last row or column counted twice, rows summed before column pairs, integers rounded half to even in integer arithmetic;
  - level k made from level k−1, never from level 0 again;
  - levels until one tile covers the image (`pyramid_factors`).

  `tests/reduce.test.mjs` checks the kernels exactly against vectors written by Python's own `reduce2` (`bench/reduce_vectors.py`): uint8/16/32, int8/16/32 and float32 blocks with odd and even sides, rounding ties, negatives and extremes.
- **Band workers.** A job is one band of level 0. For a tiled file, that is a tile row and a run of tiles. For a stripped file, a strip spans every column, so a job is the full width and as many rows as 16 MB holds, in steps of the coarsest factor (64 here), so that every level's part of a band is whole. Each band worker opens the file itself, reads and decodes its band, and makes every level's part of it. One coordinator worker owns the OPFS files: it pastes parts into 1024² tiles, hands each finished tile to a band worker to deflate, and appends the bytes to its level's file.
- **Reading.** Tiles and compressed strips go through geotiff.js. Two layouts are read directly instead (`lib/tiffReader.js`, `region()`):
  - uncompressed strips: a row sits at a fixed offset, so a band costs one read per strip it crosses (geotiff.js would read each whole strip, and a plain `tifffile.imwrite` writes one strip per plane);
  - plain deflate strips: the strips a band crosses are read in one go and inflated by the browser.
- **Level 0** is copied (deflated) only from a stripped file. A tiled flat file is already random-access, and the viewer reads level 0 from it.
- **Memory.** Bands in flight are bounded to about 1.5 GB, and so is the deflate backlog (128 MB): while more than that waits, no band is read.
- **Python's reference:** `pyramidize_image` on the same file (`bench/truth_image.py`), the median of 3 runs on 16 threads, then 200 random tiles of every level and channel compared as raw samples.
- **Fixtures** (`fixtures.py flat-image`, LSP11385's level 0):

| | Size | Layouts |
|---|---|---|
| S | 3 channels × 6001 × 7003 uint16 (0.25 GB raw) | zlib strips (tifffile's own strip size: 18 rows), uncompressed (one strip per plane), 1024 tiles |
| M | 2 channels × 52923 × 45381 uint16 (9.6 GB raw) | zlib strips (2 rows a strip), uncompressed |

**S** (3 × 6001 × 7003, 0.25 GB raw): strips 0.89 s against Python's 0.77 s (1.2×); uncompressed 0.71 s against 1.05 s (0.7×); tiles 0.64 s against 0.71 s (0.9×), with level 0 read in place (36 MB written, where the others write 142 MB). Every layout: 200/200 tiles identical, no long tasks, first tile after a relaunch in 14–16 ms.

- **The browser's pyramid is Python's, value for value**, in every layout. Level 0 included where it was copied, and with Python's half-to-even rounding.
- **Time.** On a compressed stripped file the browser is a little faster than Python's 16 threads. On an uncompressed one it is 8× faster: Python spends 3 minutes there, and the browser reads rows straight from their offsets.
- **Level 0 is most of the work and most of the bytes.** A stripped file cannot serve tiles, so level 0 is copied, deflated. The output is the size of Python's own copy (3.79 against 3.82 GB). A tiled flat file keeps level 0 in place, and only the derived levels are written (S: 36 MB against 142 MB).
- **Memory.** 1.8 GB with 12 workers, 1.5 GB with 8 (5 s slower). The deflate backlog is checked before each band is read, so it overshoots its 128 MB cap (peaks of 354–415 MB). A tighter cap trades time for memory; P2b's sweep shows the same trade.
- **What it took to get here** (development runs, not recorded):
  - the first builder took 78 s on the strips: one worker per full-width band of 1024 rows, 5 workers, and one read and one inflate per strip;
  - feeding `CompressionStream` through a Blob made the browser's blob store refuse at this volume ("TypeError: Failed to fetch");
  - a level-1 deflate in JavaScript (fflate) is no faster than Chrome's own (65–67 against 78 MB/s a thread on these tiles), so the time went into spreading the work, not into a cheaper codec.

## Storage (Measured)

**Chrome's `navigator.storage.estimate()` does not report its limit.**
- In a fresh profile it reports a quota of exactly 10,737,418,240 bytes (10 GiB). This was checked in headless and headed Chrome, with and without a persistent profile, and with Chrome started directly rather than by Playwright (probe runs, not recorded).
- A worker then wrote 14.2 GB into OPFS without an error, after which the report read 25.0 GB: usage plus 10 GiB.
- This folder's records show the same: P7-M's estimate after writing 3.79 GB reads 14.5 GB.

Chrome reports the room left as at most 10 GiB, so a page cannot read the disk size from it.

So:
- the "10.7 GB quota" of the first round was this report, not a limit, and no Plexora setting was involved (there is none);
- a page should treat `QuotaExceededError`, not `estimate()`, as the signal, call `navigator.storage.persist()` so the browser does not evict derived data, and use the browser's own limit (about 60 % of the disk in Chrome);
- Firefox's limit is real: 10 % of the disk or 10 GiB, 50 % once `persist()` is granted.

## Thresholds

| Threshold | Bound | Measured (M) | |
|---|---|---|---|
| pyramidise vs Python's own conversion | ≤ 2× | 0.88× (strips), 0.12× (uncompressed) | pass |
| tiles identical to Python's | all | 200/200 per layout | pass |
| main-thread long tasks > 50 ms | ≤ 5 | 0 | pass |
| derived data survives a relaunch; first tile | ≤ 1 s | 14 ms (every layout, S and M) | pass |
| room the browser reports ≥ what was written | ≥ 3.79 GB | 10.7 GB | pass (weak: Chrome always reports 10 GiB of room; see "Storage") |
| STOP: build > 5 min; pyramid lost across a relaunch | | no | |

The plan's "3/3 restarts" is one relaunch per layout here: five relaunches over S and M, every one with the pyramid intact. Edge and Firefox were not relaunched; Firefox builds and reads the pyramid in P8.

## Consequence

- **Flat images join flat masks:** both become pyramids in the tab, in about Python's time or less, with Python's numbers. "Prepare first" (mode E) is not needed for a 10 GB flat image.
- **Disk:** a stripped flat image costs about its compressed size again in OPFS. A tiled one costs a third of a level-0 copy. The page asks for persistence and handles `QuotaExceededError` (below).
