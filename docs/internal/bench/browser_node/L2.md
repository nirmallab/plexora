# L2: whole-slide formats through openslide-js

Date: 2026-11-07. Records: `L2-2026-11-07-a.json`, `L2-2026-11-07-b.json` (Chrome, two rounds),
`L2-2026-11-07-firefox.json`, `L2-2026-11-07-webkit.json`, `L2-2026-11-07-sakura.json`.

Verdict: **GO for MRXS, NDPI and SVS (JPEG 2000 and JPEG)** through openslide-js on the website,
and integrated (below). **Not through openslide-js:** Ventana BIF (OpenSlide itself refuses the
public slide), DICOM (OpenSlide reads brightfield JPEG DICOM only; the desktop's own wsidicom
reader reads more, so the website uses that, plan L3, integrated below), **Sakura: NO-GO with beta.5** (no public
slide exists; on a synthetic one native OpenSlide opens, openslide-js traps at open).

## Question

Plan item L2 and user decision 7: does openslide-js (OpenSlide compiled to WebAssembly) exist as
described, and does it read MRXS, NDPI, Sakura, SVS-JPEG 2000 and brightfield DICOM in the page as
native OpenSlide does, at a usable speed? The fallback, if not, was a Python port of OpenSlide's
MIRAX reader (`server/utils/mirax_reader.py`, about 4 engineer-weeks).

## Set-up

- **Slides:** the smallest public slide per format from OpenSlide's test data (CC0-1.0), sha256
  checked: Mirax `CMU-1-Saved-1_16` (3.8 MB), `Mirax2-Fluorescence-2` (41 MB, three fluorescence
  channels OpenSlide composes as RGB), `CMU-1` (565 MB, a real 109,240 x 220,696 slide); Hamamatsu
  `CMU-1.ndpi` (198 MB); Aperio `JP2K-33003-1.svs` (64 MB, JPEG 2000 YCbCr) and
  `CMU-1-Small-Region.svs` (JPEG, the control); Ventana `Ventana-1.bif` (227 MB, the smallest BIF);
  DICOM `JP2K-33003-1-v2` (66 MB, JPEG 2000) and `Leica-4` (85 MB, JPEG, sparse tiling). OpenSlide
  publishes **no Sakura slide** (its index has none; none found elsewhere).
- **Truth:** openslide-python 1.4.7 on OpenSlide **4.0.0** (`openslide-bin` 4.0.0.13, the build
  openslide-js pins), in a venv of its own (`bench/truth_l2.py`); the plexora env is unchanged. A
  second truth on OpenSlide 4.0.1 (the current openslide-bin) differs from 4.0.0 only in two
  properties (below).
- **Page:** `bench/l2_page/` loads the package's ESM build unbundled, cross-origin isolated
  (`tools/browser_build/serve.py`), 4 decode workers; `bench/l2.mjs` fetches a slide's files into
  `File` objects (as a pick gives them; a multi-file slide as `VirtualFile` entries relative to the
  index file's folder) and reads the regions the truth read.
- **Pixels:** 24-40 regions of up to 512 x 512 per slide on every level (centre, origin, random),
  compared as raw RGBA bytes (`bench/compare_l2.py`). The rule: **identical bytes**, because both
  sides are the same OpenSlide and codec builds; otherwise (a different decoder) max |diff| <= 2 and
  PSNR >= 45 dB, reported as such. Metadata: level count, every level's size, every downsample,
  every property key and value, associated image names.
- **Timing:** a "tour" of viewer-sized 1024 x 1024 tiles over the middle of the scanned area
  (`openslide.bounds-*`), a 6 x 6 grid at level 0 and at the level nearest 4x, read one at a time
  (first touch, then again) on both sides, and in the page also spread over the slide opened on 4
  workers, all in flight. Rounds A and B in ABAB order (native, page, native, page), nothing else
  running. Windows 11, i9, Chrome 156 headless; Firefox 159 and WebKit 27.2 (Playwright's builds)
  for function.

(Round B shown; round A agrees within a few ms, both in the JSON.) Open: 3-35 ms native, 5-115 ms
in the page (the mount hands the files to the broker); the first `initialize()` (wasm compile, 5
workers) 127-150 ms from a local server.

- **openslide-js is OpenSlide, byte for byte.** Every region of every slide both open is identical
  to native OpenSlide 4.0.0, alpha included, and every property matches. Against OpenSlide 4.0.1
  only two properties differ, both added in 4.0.1: `openslide.associated.thumbnail.icc-size` (SVS)
  and `openslide.barcode` (DICOM).
- **Speed is native's order.** Tour p50 is 0.55-1.8x native, one tile at a time (NDPI faster in
  the page: its restart-marker reads go through the broker's block cache). Spread over 4 opened
  copies, the page reads a tile every 6-12 ms for MRXS/NDPI, 34-47 ms for the JPEG 2000 and DICOM
  slides. Every p95 is under the envelope's 150 ms tile bar.
- **Firefox 159 and WebKit 27.2 (Windows) give the same bytes** on MRXS, NDPI, SVS-JP2K and DICOM
  (every region identical), at 1-2x Chrome's time.
- **The failures are OpenSlide's, not the port's:** native 4.0.0 and 4.0.1 refuse the same two
  slides with the same messages. Both test slides are newer than OpenSlide 4.0 (the BIF from a DP
  200 scanner, the DICOM a JPEG 2000 YBR_FULL_422 conversion).
- **DICOM beyond brightfield JPEG:** OpenSlide also refuses a synthetic H&E and a synthetic
  three-channel fluorescence DICOM slide (`tests/dicom_fixtures.py`, uncompressed). OpenSlide reads
  brightfield DICOM only.

### The desktop's reader against OpenSlide

The desktop reads `.svs`, `.ndpi` and `.bif` with tifffile and imagecodecs (`brightfield.open_rgb`),
and `.mrxs`/`.svslide` with OpenSlide. On the same regions at the levels both hold
(`bench/desktop_vs_openslide_l2.py`, RGB over white):

| Format | Identical | Max \|diff\| | Min PSNR |
|---|---|---|---|
| SVS JPEG | 26/26 | 0 | - |
| SVS JPEG 2000 (33003) | 0/10 | 1 | 51.5 dB |
| NDPI | 16/28 | 8 | 49.9 dB |
| BIF | reads (tifffile: "BIF series tiles are not stitched") | | |

So a website that reads NDPI and SVS-JPEG 2000 with openslide-js draws what the desktop draws to
within a JPEG decoder's rounding (one level for JPEG 2000; up to eight at a few NDPI pixels), and
draws native OpenSlide's pixels exactly.

### Sakura, on a synthetic slide

With no Sakura slide to be had, `bench/sakura_fixture.py` writes one as OpenSlide 4.0.0's
`vendor-sakura.c` reads it (an SQLite database: the image table named in
`DataManagerSQLiteConfigXPO`, `++MagicBytes`, a `Header`, every tile as three grayscale JPEGs under
`T;x|y;downsample;colour;plane`, the slide and scan tables, label and overview JPEGs; 3000 x 2200,
256-px tiles, 5 levels). **Native OpenSlide 4.0.0 opens it** (vendor `sakura`, 5 levels, mpp 0.25,
label/macro/thumbnail). **openslide-js 1.0.0-beta.5 does not:** its open throws `function signature
mismatch`, a WebAssembly indirect-call type trap inside OpenSlide -- the class of bug its
`openslide.patch` fixes for eight GLib sort callbacks; one on Sakura's path is evidently left. To
report upstream with the fixture. Until then the website says "Sakura slides do not open on the
website yet; open this one in the Plexora desktop app" (`services/browserSlides.js`), and opens
them once a fixed build is vendored. A Python reader is the other way (SQLite and grayscale JPEGs;
Pyodide ships `sqlite3`), not built.

## On the website (integrated)

How it is built: `client/external/openslide-js-1.0.0-beta.5/` (the package's runtime files,
unchanged, with `LICENSE`, `NOTICE` and `SOURCE`); `client/src/js/node/slideReader.js` (one
openslide-js pool, the slide opened on each decode worker, reads round them) and
`node/slideTiles.js` (brightfield.py's tile arithmetic); `services/browserSlides.js` answers
Python's `slide` and `slide_region` questions and cuts the browser node's `rgb` tiles; in Python
`providers/browser.py` `PageSlide` stands where `openslide.OpenSlide` stands on the desktop, so
`brightfield.open_rgb` is unchanged above it (`_page_slide`, `PAGE_SLIDE_SUFFIXES`: .mrxs .svslide
.ndpi .svs; an SVS/NDPI OpenSlide refuses goes back to tifffile). `node_spec` describes such a
slide (`kind: "slide"`, `brightfield.page_tile_layout`) and the browser node draws every tile
`_Level.read_rgb` would not resample; the rest are Python's, read through the same page, so the
two cannot disagree. An MRXS pick asks for the folder beside it (`services/pickedFiles.js`).

Measured in headless Chrome, picked as a user picks (`tests/browser/slides.mjs`, the run in
`tests/test_browser_slides.py`; one pass, indicative timings):

| Slide | Import | Viewer drawn | Tiles checked | By the browser node | Node tile p50 | Python's (resampled) p50 |
|---|---|---|---|---|---|---|
| MRXS CMU-1-Saved-1_16 | 0.60 s | 1.9 s | 15 | 8 | 17.6 ms | 44 ms |
| MRXS CMU-1 (565 MB) | 0.59 s | 1.9 s | 27 | 18 | 14.7 ms | 41 ms |
| MRXS Mirax2-Fluorescence-2 | 0.58 s | 1.1 s | 27 | 22 | 14.7 ms | 6 ms |
| NDPI CMU-1 | 0.51 s | 1.6 s | 21 | 21 | 31.2 ms | - |
| SVS JP2K-33003-1 | 0.51 s | 2.3 s | 18 | 7 | 47.7 ms | 149 ms |
| SVS CMU-1-Small-Region | 0.52 s | 2.3 s | 9 | 3 | 27.8 ms | 8 ms |

Before this, the website read NDPI and SVS-JPEG 2000 with tifffile in its Python, a tile at a
time: CMU-1.ndpi's viewer took 4.7 s with overview tiles of 2-3 s each, JP2K-33003-1.svs's 2.7 s
with tiles of ~1 s; an MRXS did not open ("needs OpenSlide"). **Every tile, the browser node's and
Python's, is byte for byte brightfield.py over native OpenSlide 4.0.0** (`tests/browser/
slides_truth.py`) -- for MRXS the desktop's own tile; for NDPI/SVS the desktop reads with tifffile,
within the decoder rounding measured above. The fluorescence MRXS is drawn as OpenSlide composes it
over white, as on the desktop (mostly unscanned slide).

## DICOM on the website (plan L3)

The desktop's own reader, not openslide-js: `server/utils/dicom_wsi.py` (pydicom, wsidicom) in a
new `dicom` stage (`plexora/browser/stages.py`: pydicom 3.0.2, wsidicom 0.35.0, dicomweb-client
0.61.2, marshmallow 4.3.1, cachetools 7.1.8 as wheels; requests and retrying from Pyodide; 3.25 MB
stored), loaded the first time Plexora imports pydicom. Two things it needed: `imagecodecs_shim`
now carries the names wsidicom imports (`JPEG8` with its `CS` colour spaces, `JPEG2K`, `JPEGLS`,
`JPEGXL` with `.available`, refusing stand-ins for codecs the browser lacks), so wsidicom decodes
frames there -- JPEG by Pillow, JPEG 2000 by the page's OpenJPEG; and `browser/boot.py` gives
Pyodide a stand-in `venv` module (wsidicom 0.35 imports `logger` from it by mistake). A slide is
picked with the landing's Folder. Measured (`tests/test_browser_dicom.py`, one pass):

| Slide | Import | Viewer drawn | Tiles checked | Python tile p50 / max | Against the desktop |
|---|---|---|---|---|---|
| synthetic fluorescence, 3 markers, uncompressed | 1.0 s | 2.1 s | 15 (all 3 channels) | 13 / 56 ms | identical |
| synthetic H&E, uncompressed | 1.0 s | 1.8 s | 5 | 20 / 71 ms | identical |
| Leica-4 (JPEG, sparse, 85 MB) | 14.9 s | 20.3 s | 11 | 60 / 193 ms | PSNR >= 56 dB, max 11 at a pixel (Pyodide's Pillow is not libjpeg-turbo) |
| JP2K-33003-1-v2 (JPEG 2000 YBR, which OpenSlide refuses) | 1.0 s | 2.6 s | 11 | 77 / 263 ms | within the test's bar (PSNR >= 45 dB, max <= 16) |

In CPython, wsidicom with the shim in imagecodecs' place reads the Leica tiles byte for byte as
with imagecodecs (the shim's Pillow there is libjpeg-turbo). The Leica import's 15 s is wsidicom
scanning 85 MB of sparse instances through the worker's file reads; not looked into further.
Brightfield DICOM tiles stay Python's (the browser node does not cut them); openslide-js could for
brightfield JPEG DICOM (identical to OpenSlide, above), as a later speed-up.
