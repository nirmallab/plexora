# L2: whole-slide formats through openslide-js

Date: 2026-11-07. Records: `L2-2026-11-07-a.json`, `L2-2026-11-07-b.json` (Chrome, two rounds),
`L2-2026-11-07-firefox.json`, `L2-2026-11-07-webkit.json`.

Verdict: **GO for MRXS, NDPI and SVS with JPEG 2000 tiles** through openslide-js on the website.
**Not through openslide-js:** Ventana BIF (OpenSlide itself refuses the public slide), DICOM
(OpenSlide reads brightfield JPEG DICOM only; the desktop's own wsidicom reader reads more, so the
website uses that, plan L3), Sakura SVSlide (no public slide exists to test; wired, untested).

## Question

Plan item L2 and user decision 7: does openslide-js (OpenSlide compiled to WebAssembly) exist as
described, and does it read MRXS, NDPI, Sakura, SVS-JPEG 2000 and brightfield DICOM in the page as
native OpenSlide does, at a usable speed? The fallback, if not, was a Python port of OpenSlide's
MIRAX reader (`server/utils/mirax_reader.py`, about 4 engineer-weeks).

## Set-up

- **Slides:** the smallest public slide per format from OpenSlide's test data (CC0-1.0), sha256
  checked: Mirax `CMU-1-Saved-1_16` (3.8 MB), `Mirax2-Fluorescence-2` (41 MB, three fluorescence
  channels OpenSlide composes as RGB), `CMU-1` (565 MB, a real 109,240 x 220,696 slide); Hamamatsu
  `CMU-1.ndpi` (198 MB); Aperio `JP2K-33003-1.svs` (64 MB, JPEG 2000 YCbCr) and
  `CMU-1-Small-Region.svs` (JPEG, the control); Ventana `Ventana-1.bif` (227 MB, the smallest BIF);
  DICOM `JP2K-33003-1-v2` (66 MB, JPEG 2000) and `Leica-4` (85 MB, JPEG, sparse tiling). OpenSlide
  publishes **no Sakura slide** (its index has none; none found elsewhere).
- **Truth:** openslide-python 1.4.7 on OpenSlide **4.0.0** (`openslide-bin` 4.0.0.13, the build
  openslide-js pins), in a venv of its own (`bench/truth_l2.py`); the plexora env is unchanged. A
  second truth on OpenSlide 4.0.1 (the current openslide-bin) differs from 4.0.0 only in two
  properties (below).
- **Page:** `bench/l2_page/` loads the package's ESM build unbundled, cross-origin isolated
  (`tools/browser_build/serve.py`), 4 decode workers; `bench/l2.mjs` fetches a slide's files into
  `File` objects (as a pick gives them; a multi-file slide as `VirtualFile` entries relative to the
  index file's folder) and reads the regions the truth read.
- **Pixels:** 24-40 regions of up to 512 x 512 per slide on every level (centre, origin, random),
  compared as raw RGBA bytes (`bench/compare_l2.py`). The rule: **identical bytes**, because both
  sides are the same OpenSlide and codec builds; otherwise (a different decoder) max |diff| <= 2 and
  PSNR >= 45 dB, reported as such. Metadata: level count, every level's size, every downsample,
  every property key and value, associated image names.
- **Timing:** a "tour" of viewer-sized 1024 x 1024 tiles over the middle of the scanned area
  (`openslide.bounds-*`), a 6 x 6 grid at level 0 and at the level nearest 4x, read one at a time
  (first touch, then again) on both sides, and in the page also spread over the slide opened on 4
  workers, all in flight. Rounds A and B in ABAB order (native, page, native, page), nothing else
  running. Windows 11, i9, Chrome 156 headless; Firefox 159 and WebKit 27.2 (Playwright's builds)
  for function.

## Results (Measured)

| Slide | Opens (native / page) | Metadata | Pixels | Tour tile p50 / p95, ms (native / page) | Page, 4 opens, ms/tile |
|---|---|---|---|---|---|
| MRXS CMU-1-Saved-1_16 | both | identical (350 properties) | 36/36 identical | 2.7 / 30.4 vs 4.5 / 31.7 | 6.3 |
| MRXS Mirax2-Fluorescence-2 | both | identical | 40/40 identical | 12.4 / 39.7 vs 22.6 / 55.0 | 11.4 |
| MRXS CMU-1 (565 MB) | both | identical | 40/40 identical | 1.5 / 64.3 vs 2.1 / 94.6 | 5.7 |
| NDPI CMU-1 | both | identical | 36/36 identical | 29.8 / 54.9 vs **16.3 / 34.3** | 11.5 |
| SVS JP2K-33003-1 | both | identical | 30/30 identical | 55.4 / 94.6 vs 65.8 / 118.9 | 46.6 |
| SVS CMU-1-Small-Region (JPEG) | both | identical | 26/26 identical | 16.1 / 18.5 vs 17.4 / 22.4 | 7.8 |
| DICOM Leica-4 (JPEG) | both | identical | 30/30 identical | 21.0 / 82.6 vs 33.1 / 99.1 | 34.2 |
| BIF Ventana-1 | **neither**: `Bad direction attribute "LEFT"` | | | | |
| DICOM JP2K-33003-1-v2 | **neither**: `Unsupported photometric interpretation YBR_FULL_422` for JPEG 2000 | | | | |

(Round B shown; round A agrees within a few ms, both in the JSON.) Open: 3-35 ms native, 5-115 ms
in the page (the mount hands the files to the broker); the first `initialize()` (wasm compile, 5
workers) 127-150 ms from a local server.

- **openslide-js is OpenSlide, byte for byte.** Every region of every slide both open is identical
  to native OpenSlide 4.0.0, alpha included, and every property matches. Against OpenSlide 4.0.1
  only two properties differ, both added in 4.0.1: `openslide.associated.thumbnail.icc-size` (SVS)
  and `openslide.barcode` (DICOM).
- **Speed is native's order.** Tour p50 is 0.55-1.8x native, one tile at a time (NDPI faster in
  the page: its restart-marker reads go through the broker's block cache). Spread over 4 opened
  copies, the page reads a tile every 6-12 ms for MRXS/NDPI, 34-47 ms for the JPEG 2000 and DICOM
  slides. Every p95 is under the envelope's 150 ms tile bar.
- **Firefox 159 and WebKit 27.2 (Windows) give the same bytes** on MRXS, NDPI, SVS-JP2K and DICOM
  (every region identical), at 1-2x Chrome's time.
- **The failures are OpenSlide's, not the port's:** native 4.0.0 and 4.0.1 refuse the same two
  slides with the same messages. Both test slides are newer than OpenSlide 4.0 (the BIF from a DP
  200 scanner, the DICOM a JPEG 2000 YBR_FULL_422 conversion).
- **DICOM beyond brightfield JPEG:** OpenSlide also refuses a synthetic H&E and a synthetic
  three-channel fluorescence DICOM slide (`tests/dicom_fixtures.py`, uncompressed). OpenSlide reads
  brightfield DICOM only.

### The desktop's reader against OpenSlide

The desktop reads `.svs`, `.ndpi` and `.bif` with tifffile and imagecodecs (`brightfield.open_rgb`),
and `.mrxs`/`.svslide` with OpenSlide. On the same regions at the levels both hold
(`bench/desktop_vs_openslide_l2.py`, RGB over white):

| Format | Identical | Max \|diff\| | Min PSNR |
|---|---|---|---|
| SVS JPEG | 26/26 | 0 | - |
| SVS JPEG 2000 (33003) | 0/10 | 1 | 51.5 dB |
| NDPI | 16/28 | 8 | 49.9 dB |
| BIF | reads (tifffile: "BIF series tiles are not stitched") | | |

So a website that reads NDPI and SVS-JPEG 2000 with openslide-js draws what the desktop draws to
within a JPEG decoder's rounding (one level for JPEG 2000; up to eight at a few NDPI pixels), and
draws native OpenSlide's pixels exactly.
