# P3: a cell table in the browser node

Date: 2026-11-05. Records:
- `P3-{S,M,L}-2026-11-05.json`: the column store, the design adopted;
- `P3-{M,L}-2026-11-05-parquet.json`: the first design, a Parquet copy;
- `P3B-L-2026-11-05.json`: where cold-ingest time goes.

Verdict: **PARTIAL**. Every threshold passes but one: a first-ever open of a CSV costs 5–10× polars' read of the same file. That is no STOP condition.

## Question

Can a CSV be read in the browser, kept for the next visit, and answer the viewer's five questions exactly as the server does, in bounded time and memory? The five questions are: all cells (ids and coordinates), one column, describe, the nearest cell, and ROI → cells, plus a gate count.

## Set-up

- **Ingest:**
  1. DuckDB-Wasm (1.33, single-threaded: the page is not cross-origin isolated) parses the picked file (`CREATE TABLE … AS read_csv`).
  2. Each numeric column goes out as a raw float64 file into OPFS, ids and coordinates first, plus a manifest. This is the browser's twin of the server's derived frame.
  3. A reopen reads the three columns a first draw needs, without starting DuckDB.
- **The five questions** run on typed arrays with the server's rules (`page/src/table.js`):
  - `_all_cells_from_frame`: interleaved, numpy-truncating to uint32;
  - `_describe_column`: finite only, numpy linear percentiles by quickselect, numpy's exact histogram bin assignment, float64 mean, ddof 1;
  - `SpatialIndex.nearest`: kdbush in place of cKDTree;
  - `roi/mapping.assign`: strictly within, by ray casting over kdbush candidates;
  - float32 gate comparisons.
- **References:**
  - all_cells, columns and describe come from `plexora node serve`, with the page pushing the read spec (the page is the primary);
  - nearest (200 points), ROI (20 polygons of 10, 100 and 1000 vertices) and gates (20) come from `bench/truth_table.py` (scipy, shapely, numpy);
  - "polars' read" is `pl.read_csv` of the same file on the same machine.
- **Fixtures:** S is exemplar-001 (11,201 × 22, 4 MB); M is LSP11385 (202,049 × 50, 180 MB); L is Orion CRC02 (1,260,592 × 29, 634 MB).
- A cold open has OPFS cleared and a fresh profile. A reopen is the same profile with Chrome relaunched on the same origin. The origin includes the port, so the static server keeps one port across the relaunch.

| … of which DuckDB start (s) | 0.42 | 0.43 | 0.48 |
| … of which CSV parse (s) | 0.18 | 1.01 | 2.61 |
| Cold: every column stored (s) | 0.93 | 2.35 | 4.68 |
| polars' read of the same file (s) | 0.16 | 0.31 | 0.34 |
| the node's table load (s) | 0.01 | 0.22 | 0.26 |
| **Reopen after a relaunch (ms)** | 14 | 19 | **31** |
| describe, every column (ms) | 74 | 419 | 882 |
| an uncached column (ms, worst of 5) | 5 | 4 | 10 |
| kd-tree build (ms) | 10 | 50 | 212 |
| nearest cell (ms, worst of 200) | 0.6 | 2.2 | 4.0 |
| ROI → cells (ms, worst of 20; 1000-vertex polygons) | 44 | 28 | 55 |
| peak renderer working set (GB) | 0.36 | 0.75 | 1.67 |
| OPFS bytes / CSV bytes | 0.49 | 0.45 | 0.46 |

**Identity**, on every fixture:
- all_cells bytes are identical to the node's;
- 5 float32 columns are identical;
- describe matches to 1e-12 relative or better (float64);
- 200/200 nearest cells, 20/20 ROI row sets (SHA-256 of the sorted rows) and 20/20 gate counts agree.

**Where cold-ingest time goes** (P3b, L):

| Path | s |
|---|---|
| DuckDB COPY CSV → zstd Parquet (the first design) | 10.5 |
| DuckDB CSV → in-memory table (parse only) | 2.3 |
| DuckDB SELECT id, x, y FROM read_csv | 1.6 |
| Parquet write from an already-parsed table: zstd / snappy / none | 8.2 / 7.5 / 7.7 |
| A numeric CSV parsed by 8 workers in JavaScript | 11.9 |

- **The time is Parquet encoding, not CSV parsing.** Single-threaded wasm spends about 8 s writing 1.26 M × 29 doubles as Parquet whatever the codec.
- **The first design fails P3 four ways.** Parquet is what it kept:

| L | Parquet store | Column store |
|---|---|---|
| cold load (s) | 12.1 | 4.7 |
| reopen (ms) | 885 | 31 |
| describe (ms) | 2173 | 882 |
| peak renderer (GB) | 2.35 | 1.67 |

- **A parallel JavaScript parser was slower than DuckDB's.** It was bit-identical, but it hit the slow `Number()` path on these files' 17-digit values, so it was dropped.

## Consequence

- **A first open of a 1.26 M-cell CSV costs about 3.4 s before cells draw**, once. Every later open costs 31 ms.
- **The miss is single-threaded wasm.** Cross-origin isolation would let DuckDB use threads (investigation §3, Phase 4); P5(d) shows a node's tiles survive it.
- **Extrapolation (Predicted).** The parse is linear in values, so Visium HD-scale tables (19.9 M × 10) would take about 15 s to parse once. That is still workable; the 4 GB wasm32 ceiling, not time, is the next limit to measure (an XL run).
