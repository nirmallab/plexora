# P3: a cell table in the browser node

Date: 2026-11-05 (two rounds the same day; the records are the second round's). Records:
- `P3-{S,M,L}-2026-11-05.json`: the column store, with the CSV parsed by plain workers (the design adopted);
- `P3-L-2026-11-05-duckdb.json` and `-duckdb-par4.json`: the same store with DuckDB-Wasm parsing, in one instance (the first round's design) and in four;
- `P3-{M,L}-2026-11-05-parquet.json`: the first design of all, a Parquet copy;
- `P3B-L-2026-11-05.json`: the JavaScript parser against DuckDB's parse, bit for bit, and where ingest time goes.

Verdict: **GO** on S, M and L. The first round was PARTIAL: a first-ever open cost 5–10× polars' read of the same file. Parsing in plain workers brings it to 0.8–2.7×.

## Question

Can a CSV be read in the browser, kept for the next visit, and answer the viewer's five questions exactly as the server does, in bounded time and memory? The five questions are: all cells (ids and coordinates), one column, describe, the nearest cell, and ROI → cells, plus a gate count.

## Set-up

- **Ingest** (`page/src/table.js`, `ensureColumnStore`):
  1. The first MB gives the column names, the delimiter (comma or tab) and which columns are numbers (every non-empty value in it parses as one).
  2. The file is cut at line starts into parts: one per 16 MB, up to the cores less two, at most 16.
  3. Each part goes to a plain worker (`workers/csvWorker.js`). It reads 8 MB at a time, decodes each piece once as Latin-1, and hands every field to `Number()` as a substring of that one string. V8's `Number()` is correctly rounded, so a value is the double polars or DuckDB reads. Empty fields, `nan` and `inf` read as polars reads them. Anything else that is not a number is counted, and a column the head called numeric that holds text further down is dropped.
  4. Each numeric column goes out as a raw float64 file into OPFS, ids and coordinates first (the load is "drawable" once they are on disk), plus a manifest.
  5. A reopen reads the three columns a first draw needs, starting nothing.
- **Refusals.** A quoted field anywhere in the head sends the file to DuckDB-Wasm instead (a cut could land inside a quoted line break). So does a Parquet file. `--params '{"parser":"duckdb","parallel":N}'` forces it.
- **The five questions** run on typed arrays with the server's rules:
  - `_all_cells_from_frame`: interleaved, numpy-truncating to uint32;
  - `_describe_column`: finite only, numpy linear percentiles by quickselect, numpy's exact histogram bin assignment, float64 mean, ddof 1;
  - `SpatialIndex.nearest`: kdbush in place of cKDTree;
  - `roi/mapping.assign`: strictly within, by ray casting over kdbush candidates;
  - float32 gate comparisons.
- **References:**
  - all_cells, columns and describe come from `plexora node serve`, with the page pushing the read spec (the page is the primary);
  - nearest (200 points), ROI (20 polygons of 10, 100 and 1000 vertices) and gates (20) come from `bench/truth_table.py` (scipy, shapely, numpy);
  - "polars' read" is `pl.read_csv` of the same file on the same machine, on all its cores.
- **Fixtures:** S is exemplar-001 (11,201 × 22, 4 MB); M is LSP11385 (202,049 × 50, 180 MB); L is Orion CRC02 (1,260,592 × 29, 634 MB).
- A cold open has OPFS cleared and a fresh profile. A reopen is the same profile with Chrome relaunched on the same origin (the origin includes the port, so the static server keeps one port across the relaunch).

**Identity**, on every fixture and with either parser:
- all_cells bytes are identical to the node's;
- 5 float32 columns are identical;
- describe matches to 3e-12 relative or better (float64);
- 200/200 nearest cells, 20/20 ROI row sets (SHA-256 of the sorted rows) and 20/20 gate counts agree.

**The JavaScript parser against DuckDB's parse (P3b, L).** All 29 columns, 1,260,592 rows each, are bit-identical (0 values differ), including the 17-digit marker means. The parse alone takes 1.42 s in 4 workers and 0.94 s in 12. DuckDB on the same file: `CREATE TABLE … AS read_csv` 2.36 s; a 3-column projection 1.57 s; Parquet from the parsed table 7.5–7.9 s whatever the codec; `COPY` to zstd Parquet 10.7 s.

**Why DuckDB stopped being the parser.**
- One instance spends 2.7 s parsing L, single-threaded: the page is not cross-origin isolated.
- Four instances, each parsing a quarter of the lines, cut the parse to 0.95 s. But each costs about 0.5 s to start (all four start together) and its own wasm heap, so the load is still 5.3× polars and the tab peaks at 2.84 GB, over the 2 GB bound. Eight instances were slower and heavier again in a development run (2.0 s, 3.2 GB; not recorded).
- Plain workers start in milliseconds and keep only the columns. The parse is 0.7 s in 16 workers, and the tab peaks at 1.09 GB, below the first round's 1.67 GB.
- The first version of the JavaScript parser (first round) was 11.9 s, slower than DuckDB. It decoded every field into a string on its own, which costs twice `Number()`'s own time per field. One decode per 8 MB piece and a substring per field is 116 ns a field on this machine (a Node microbenchmark over 64 MB of L, not recorded).
- DuckDB stays for what a hand-written parser should not take on: quoted CSVs, and SQL if Plexora ever needs it. Its Parquet reader is an extension it downloads from `extensions.duckdb.org` on first use (P4), so Parquet goes to hyparquet.

**The first design, a Parquet copy** (`-parquet` records): L loads in 12.1 s and reopens in 0.9 s. Single-threaded wasm spends about 8 s encoding Parquet for 1.26 M × 29 doubles, whatever the codec. It was replaced by the raw column store in the first round.

## Consequence

- **A first open of a 1.26 M-cell CSV costs about 0.9 s before cells draw**, once, and 1.75 s until every column is stored. Every later open costs tens of ms.
- **No cross-origin isolation is needed** for the table path (it was the first round's suggested fix).
- **Extrapolation (Predicted).** The parse is linear in values: Visium HD-scale tables (19.9 M × 10) would take about 4 s to parse once on this machine. The 4 GB wasm32 ceiling no longer applies to the CSV path, since nothing runs in wasm. The column store's own size (8 bytes a value: 1.6 GB at 19.9 M × 10) is the next limit to measure (an XL run).
