# L11 (+ L4): volumes, surfaces and bricks on the website

Date: 2026-11-07. Branch `web/volumes`. Harness: `tests/browser/volume.mjs` with
`tests/browser/volume_web.py` (fixtures, operations, comparison); pytest wrapper
`tests/test_browser_volume.py`. Raw records: `C:/plexora-bench-vol/runs/bench/*/record.json`
(not in the repository).

**Verdict: works.** Every z-stack format opens in the website's 3-D view and
every volume answer the viewer asks is the desktop's, byte for byte (a PNG tile
pixel for pixel). Surfaces and 3-D objects are made and served on the website,
the same meshes and tables as the desktop's. What is slow is what was expected:
the numba kernels running as Python (plan L5), up to 460x the desktop on cell
surfaces.

## What works

| Z-stack | Opened, 3-D drawn | Answers held to the desktop's |
|---|---|---|
| OME-TIFF stack (tiled, deflate, SubIFD levels) + 3-D label mask | yes | 18 of 18 (15 bytes, 3 tile pixels) |
| OME-Zarr 0.4 folder (picked as a tree) | yes | 17 of 17 |
| Imaris, deflate + shuffle, uint16 | yes | 16 of 16 |
| Imaris 10 LZ4, uint16 | yes | 16-17 of 16-17 |
| Imaris 10 LZ4, uint8 | yes | 17 of 17 |

What each run does:
- picks the files in Chrome (an OME-Zarr folder as its tree), as the picker does;
- runs `/import/inspect` and `/import/sample`, then opens the viewer;
- waits for the exact windows, then enters 3-D (`viewState.set({mode: "volume"})`);
- asks the same addresses of both arms, and of the viewer's own requests the ones both made:
  - `/volume/<ds>/info`, `/window`, `/bricks/manifest`;
  - `/level`: auto and coarsest, per channel, u8, plus auto f16;
  - `/bricks`: the first 8 bricks at the finest level, every brick of the coarsest;
  - two `/section` geometries;
  - tiles with `view=` (plane, projection, section) at `q=hd`;
  - `/volume/<ds>/objects`.
- **Pixels.** The 3-D canvas is read back (`createImageBitmap`). Then it is read again through the renderer's capture path (`whenSettled` + `renderFrame`) and set beside the desktop's as a 32x32 grid of block means: 0.004-0.17 apart out of 255. Screenshots: `3d.png`, `3d-settled.png`, `3d-surface.png`.
- **The operations** (`--ops`, `volume_web.OPS`):
  - an isosurface, through `store.extract_isosurface`;
  - the mask's cell surfaces, through `_build_label_surfaces`;
  - the objects, through `objects.measure_project_objects`.

  Each is run in the website's Python and in CPython with and without numba, and each kernel is timed at its call. Results:
  - **Meshes:** topology and vertex positions are identical.
  - **Object tables:** identical.
  - **Mesh measurements:** identical to 12 significant digits. `equivalent_diameter_um` differs in its last bit: a cube root, libm's.
- **The surface route.** `POST /volume/<ds>/surfaces` builds the surface on the website between requests. It needs a throwaway Pro licence trusted in that Python only, as conftest's issuer does. Its mesh, objects and manifest are then served, and the reopened 3-D view draws it: test scale 3.5 s, mid scale 16.4 s.

### Changes this needed

- **L4, hdf5plugin optional** (`volume/sources/ims.py`).
  - The reader's own chunk path already decoded LZ4 through `imagecodecs.lz4h5_decode`: imagecodecs_shim's on the website, which is built on `lz4`.
  - It now also decodes zstd, but only where HDF5 has no zstd filter, so a desktop with hdf5plugin is unchanged.
  - The reads that went through h5py itself go through `_region` when h5py cannot decode the filters: an import's mask verdict and an .ims mask's planes.
  - The plan's `ims_filters.py` was not needed: the decoders were already in ims.py, and the tests patch them there.
  - `ims_index.ensure` starts no process on emscripten.
- **Stages** (`browser/stages.py`, full build). Stored bytes:

  | Stage | Contents | Bytes |
  |---|---|---|
  | `hdf5` (new) | h5py, lz4 | 1.15 MB |
  | `skimage` (new) | scikit-image | 11.1 MB |
  | `qc` | OpenCV, shapely | 8.7 MB (was 19.8) |
  | `h5ad` | pandas, anndata; h5py listed again | 5.7 MB |

  - **`hdf5`:** what an .ims loads, so an .ims no longer fetches h5ad's 5.7 MB. Measured: an .ims loads `hdf5` alone, in 340 ms. lz4 (41 kB) joins h5py because no LZ4 file can be read without h5py first.
  - **`h5ad`:** h5py is listed again (a no-op load) because anndata imports it at module level, where StageFinder loads nothing. An .h5ad import now loads `hdf5` then `h5ad`: 41 kB more and one more fetch. tests/test_browser_h5ad.py is updated.
  - **`skimage`:** a surface needs marching cubes, not OpenCV.
- **Parquet** (`browser/boot.py parquet()`). Pyodide's polars has no Parquet, but objects and surface tables are Parquet files. polars' Parquet read, write and scan now go through pyarrow, and the parquet stage loads on first use.
  - It is a polars-level stand-in, like `codecs()`; under CPython it is a no-op.
  - It is cross-cutting: QC results are Parquet too.
- **32-bit numpy** (`volume/planes.py`, `surface/mesh.py`). `np.repeat` counts must cast safely to intp, and int64 does not on wasm32. They are now intp, which is the same on a 64-bit desktop.

## Website against the desktop

The bench stacks are 2 channels x 64 x 1023 x 997 uint16: one dataset written as all five formats (`volume_web.py make --scale bench`). The Imaris files have 4 levels, chunks (16, 128, 128), and coarse levels halving z.

Each case ran twice, website first and then desktop first; the table gives the mean of the two, in ms. The desktop arm is this checkout's Plexora in CPython, in the same Chrome. Rows:
- **open:** the viewer's first plane drawn.
- **3-D drawn:** from entering 3-D to the renderer ready.
- **level:** one channel's auto level, u8, asked again after the view settled.
- **brick:** one request of one brick for both channels, at the finest level: cold, then warm.

The machine was shared with six other agents' builds and tests (CPU about 75 % busy), so these are indicative.

| Stack | open W / D | 3-D drawn W / D | level W / D | brick cold p50 (p95) W / D | warm p50 W / D | website heap |
|---|---|---|---|---|---|---|
| OME-TIFF + mask | 2933 / 954 | 3932 / 2145 | 3238 / 1510 (2.1x) | 403 (637) / 85 (122) | 4 / 6 | 1.08 GiB |
| OME-Zarr | 1650 / 1452 | 3970 / 603 | 3194 / 215 (15x) | 43 (147) / 8 (26) | 5 / 4 | 0.93 GiB |
| Imaris deflate | 1281 / 1619 | 1668 / 524 | 1436 / 292 (4.9x) | 16 (34) / 7 (22) | 4 / 5 | 1.11 GiB |
| Imaris LZ4 | 1620 / 1564 | 1470 / 674 | 952 / 311 (3.1x) | 8 (37) / 6 (14) | 4 / 5 | 1.11 GiB |
| Imaris LZ4 uint8 | 1660 / 1664 | 1134 / 547 | 627 / 234 (2.7x) | 7 (9) / 6 (12) | 5 / 4 | 1.12 GiB |

- **Import** is 0.07-0.8 s on both, except TIFF with a mask: 4.8 s against 1.2 s. The mask becomes a label volume in Python.
- **Exact windows:** 0.8-3.7 s on the website. The desktop's Imaris windows are exact at once (6 ms); its TIFF and Zarr windows take 2-3.5 s.
- **OME-Zarr level reads are 15x slower:** the desktop decodes a level's chunks on threads; the website has one.
- **LZ4 is the website's fastest Imaris codec:** 0.95 s a level against 1.4 s for deflate.
- **Bricks.** Cold, an Imaris brick is within 2.3x of the desktop's and a Zarr brick 5x. A TIFF brick is 4.7x: 32 planes of tiles inflated in Python's zlib. Warm, every brick is the same, 4-6 ms.
- **One lane.** The website's Python answers one request at a time. During the TIFF open, `/volume/<ds>/info` waited 6 s behind level reads for 6 ms of its own work. Asking for the level before info (or answering info in the page) would shorten the first 3-D frame more than any decoder.

Usable: the objects (4 s) and every viewing route.

## What does not work, or was not tried

- **Since 2026-11-11 the website makes no bricks copy at all** (`PLEXORA_VOLUME_BRICKS=0`; see [WEBSITE_TAB_LIMITS.md](../../WEBSITE_TAB_LIMITS.md), which also measures a 349 GB, 70-channel .ims over SFTP).
- **Not measured: a stack that gets a bricks copy.** That is a plane-major stack of at least 2^28 voxels per channel: bench3d's `flatstack`, 1.5 GB. `volume/bricks.py` writes its coarse levels (up to 256 MB a channel) into the project folder, which on the website is the browser's store, in the worker's memory before it is synced. Measure this before claiming that size works. The heap was already 1.1 GiB after one bench stack (the chunk and level caches), against the 3 GiB wasm32 STOP.
- **Not measured: the very large OME-Zarr stacks.** These are bench3d's `medium` (3.8 GB) and `large` (8.6 TB declared). Only one 195 MB Zarr was run.
- **Covered by CPython only:**
  - zstd Imaris, and .ims masks without hdf5plugin (tests/test_ims_without_hdf5plugin.py);
  - the routes not asked here: `pin`, `plane_cells`, `section_cells`, `tracks`, `prepare`, and the surface `refine`/`export`/`import`/`neighbours`/`preview`/`suggest`.
  
  They run the same code over the same reads, but the browser has not been shown them.
- **Seen in both apps, not changed here.** On entering 3-D, the sidebar's second auto-contrast pass (the GMM fit) sometimes never lands on the slot: `viewerSidebar` `stillCurrent()` returns early. The picture then keeps the provisional contrast. This is why the harness compares pictures only when both sidebars set the same contrast.
- **Website wording.** The mask notice reads "/picked/vol1 is read-only for this account, so the cell-mask pyramid is kept in /data/stack": a desktop sentence about a picked file.
- **Other 32-bit traps.** The two `np.repeat` count casts were the ones on these paths. The same int64-to-intp `safe` cast will fail anywhere else it is used with int64 repeats or similar. A lint for `np.repeat(..., <int64>)` would find them.
