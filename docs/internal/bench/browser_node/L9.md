# L9: Google Cloud without the Google Cloud CLI

Date: 2026-11-07. Branch `web/gcloud`. Harness: `tests/browser/gcloud.mjs` against a stand-in
Google (`tests/browser/mock_google.py`); pytest wrappers `tests/test_browser_gcloud.py`,
`tests/test_gcloud_rest.py`, `tests/test_node_tls.py`. **Google's real APIs were never called
and no cloud resource was made**: everything below is measured against the stand-in, which
answers in Google's documented shapes.

**Verdict: works against the stand-in; not yet against Google** (no OAuth client exists: see
"What the OAuth client needs"). The website lists projects, buckets, a bucket's contents,
zones and instances; creates, starts, stops, resizes and deletes a VM; and hands the user to a
Plexora node on that VM, all without the CLI. The desktop is unchanged for a user with the
CLI.

## What works

| Question | Website (REST) | Desktop with gcloud | Desktop without gcloud |
|---|---|---|---|
| Who is signed in | OpenID userinfo with the page's token | `gcloud auth list` (+ a token probe) | "Install the Google Cloud CLI" (unchanged) |
| Projects | Resource Manager `projects.list` | `gcloud projects list` | -- |
| Buckets, one bucket (a public one via its objects) | Storage JSON API | `gcloud storage buckets ...` | -- |
| A bucket's contents, one folder level (new) | Storage `objects.list`, `delimiter=/` | the same JSON call with gcloud's token | -- |
| Zones, instances, one instance | Compute API | `gcloud compute ...` | -- |
| Start, stop, delete (label-checked), resize a stopped VM (new) | Compute API | `gcloud compute instances ...` | -- |
| Connect | a node VM, handed over at `https://<ip>:8443/app/` | SSH through IAP (unchanged) | -- |

- `plexora/gcloud_rest.py`: the same verbs and return shapes as `plexora/gcloud.py`, over
  urllib (the page's `fetch` on the website, `plexora/browser/fetch.py`). `gcloud.backend()` is
  the seam: REST when the request carries the page's token, and always in Pyodide; the CLI
  otherwise. Routes (`gcloud_routes.py`, `recipes._compose_gcloud`) go through it. New routes:
  `/settings/gcloud/objects`, `/settings/remotes/<n>/vm/resize`, `/settings/remotes/<n>/vm/node`;
  `/settings/remotes/<n>/vm` reports the node. On the website every `gcloud_*` endpoint is now
  `python` (was `handoff`).
- **The VM runs its own node** (no SSH from a page). `ensure_node` creates the desktop's
  deny-all rule (`plexora-deny-public-ingress`, tag `plexora`, priority 65000) and
  `plexora-allow-node-https` (tcp:8443, tag `plexora-node`, priority 1000), then a VM like the
  desktop's (Debian 13, Spot with STOP, `created-by=plexora`, storage read/write scope) whose
  startup script (`NODE_STARTUP_SCRIPT`) installs gcsfuse and Plexora, mounts the bucket
  (`--only-dir` for a folder) as an unprivileged `plexora` user and runs
  `plexora node serve --app --tls self-signed --dynamic` as a systemd service, with an idle
  shutdown timer (no connection on the port for 30 minutes). It writes `plexora/state`
  (installing, starting, ready, failed-*) and `plexora/fingerprint` as guest attributes; the
  page reads them through the Compute API, since it cannot reach a self-signed node itself.
  A stopped VM the desktop made is converted (metadata + tags) and started.
- **`plexora node serve --tls self-signed`** (`server/node/tls.py`): a P-256 certificate made
  once and kept in `<data root>/node-tls/` (so the browser's exception survives restarts), its
  SHA-256 fingerprint printed; Waitress on loopback behind a TLS front on the node's port.
- **The hand-over**: `https://<ip>:8443/app/connect#v=1&e=https://<ip>:8443&t=<node token>` --
  the node's own origin (no CORS, no local-network prompt), one certificate warning, the
  fingerprint shown beside the link to check it against. The node token is generated when the
  VM is made and lives only in the VM's metadata; the page reads it back through the API.
- **The page** (`services/googleAuth.js`, `services/googleAuthReturn.js`, `google-auth.html`):
  Sign in with Google, Signed in as, Use another account; the four-page form as on the
  desktop; a connection view that follows the VM and hands over. Settings > Remote servers
  (the SSH notice on the website) has a Google Cloud button: the saved connection, else the
  form.

Measured (`tests/browser/gcloud.mjs`, Chrome 13/13, ~25 s): the sign-in popup asked
`response_type=token` with the narrow scopes and returned to `<site>/google-auth.html`, then
closed itself; the form named the account the worker read; projects and buckets filled the
menus; Create & Connect made both rules, then the VM, and handed over the link with the VM's
token and the fingerprint; instances, a bucket's folders, stop, resize, start; the button again
reopened the saved connection; the token was in no localStorage, sessionStorage, IndexedDB
store, cookie or worker file, and every API call carried it as a bearer token; a refused token
answered `reauth`. `tests/test_gcloud_rest.py` (25) covers request shapes, refusals (404, 403,
public bucket, SERVICE_DISABLED, ZONE_RESOURCE_POOL_EXHAUSTED -> the Standard button, 401) and
the whole flow through the real urllib seam; `tests/test_node_tls.py` (3) a real
`plexora node serve --tls self-signed` over HTTPS with its token check.

## Decisions taken here

- **Scopes**: `compute`, `devstorage.read_only`, `cloudplatformprojects.readonly`, plus
  `openid email`. Resource Manager's `projects.list` accepts `cloudplatformprojects.readonly`
  (checked in its reference), so `cloud-platform` (all of Google Cloud, read and write) is never
  asked for; `devstorage.read_only` is enough because the VM, not the page, writes to the
  bucket (with its own service account). `compute` cannot be narrowed: creating and deleting
  VMs and firewall rules needs it.
- **Not Google Identity Services' script.** GIS's token client answers its popup through
  `window.opener`, which the site's `Cross-Origin-Opener-Policy: same-origin` severs, and the
  site needs that header for cross-origin isolation (plan D5). `googleAuth.js` makes the same
  request GIS makes (the authorization endpoint, `response_type=token`, hourly token, no
  refresh token) in a popup that returns to the site's own page, which hands the token back on
  a BroadcastChannel. Google documents this as the implicit flow and calls it legacy; if the
  verification review objects, the alternative is GIS in a helper page served with
  `COOP: same-origin-allow-popups` (a per-path header) -- not built.
- **The desktop keeps the CLI.** Its session is SSH through IAP with OS Login keys, which only
  the CLI carries, and Google refuses OAuth inside embedded web views, so a desktop sign-in
  needs the system browser and a second ("Desktop app") OAuth client. The REST backend answers
  on the desktop whenever a request carries a token, so the remaining work is that sign-in, not
  the backend. With the CLI installed nothing changes except one field (`backend: "cli"`) in
  the status.
- **A VM the user already runs is not turned into a node** (that needs software installed over
  SSH, with their say-so): the website says to use the desktop app for it.

## What the OAuth client needs (the user's, calendar weeks, no fee)

- A Google Cloud project owned by BioCognia; an OAuth consent screen (External, app name
  "Plexora", support email, homepage `https://plexoraapp.com`, privacy policy and terms URLs,
  authorised domain `plexoraapp.com`), and a **Web application** client with:
  - Authorised JavaScript origins: `https://viewer.plexoraapp.com` (and each preview origin);
  - Authorised redirect URIs: `https://viewer.plexoraapp.com/google-auth.html` (exactly; one per
    origin, and one per Open OnDemand base path if the app is served there).
- Scopes on the consent screen: `openid`, `email` (non-sensitive), `.../auth/compute`,
  `.../auth/devstorage.read_only`, `.../auth/cloudplatformprojects.readonly` (sensitive: Google
  verifies them -- a justification per scope, a demo video of the sign-in and of each use, the
  privacy policy saying the token is used only in the browser and never stored). None is
  restricted, so no third-party security assessment.
- Until verified: up to 100 test users, with an "unverified app" screen.
- Then: `static_build --google-client-id <id>` (shell.json `google.client_id`); nothing else
  changes.

## Security notes

- The access token lives in a closure in the tab's host document, for at most its hour; it is
  never written to storage, a cookie or a URL (the return page clears its own fragment before
  anything else runs, sends no referrer, and closes). It travels only in the
  `X-Plexora-Google-Token` header of the page's own requests to its worker, which binds it for
  that one request (a context variable reset when the request ends) and sends it to Google.
- The node token is generated per VM, lives in the VM's metadata (readable by whoever may read
  the project's instances -- who could also SSH in), reaches the node through a root-only
  environment file (never a command line), and reaches the page only to be put in the link's
  fragment, which a browser never sends.
- The node's port is open to the internet (`0.0.0.0/0`, tcp:8443 only); every data route needs
  the token (128 bits, constant-time check), and `/app/` serves only the public website code.
  The certificate is self-signed: the fingerprint beside the link is the user's check against
  a man in the middle on first use.
- Deleting a VM still needs its `created-by=plexora` label; neither backend has a storage
  deletion verb.

## What remains

- A real-Google run (needs the OAuth client): CORS on `compute.googleapis.com`,
  `storage.googleapis.com`, `cloudresourcemanager.googleapis.com` and
  `openidconnect.googleapis.com` for a bearer request from the worker (documented as supported,
  unverified here); the startup script on a real Debian 13 VM (bash-syntax-checked only).
- The PyPI wheel ships `client/dist/*` but not `client/dist/static/`, so a VM's
  `--app` has nothing to serve until the release includes the static build (built with `--py`
  pointing at the assets bucket, so the node's `/app/` can boot its Python). The startup script
  reports this as `failed-noapp` rather than handing over a 404.
- The desktop's sign-in without the CLI (system browser, loopback redirect, a "Desktop app"
  client).
- Restricting the node port to the user's own address (the page cannot learn it without a
  third-party service); a node certificate from a CA (needs a name: no DNS service by decision).
- Settings > Remote servers on the website still shows the SSH notice rather than cards; a
  saved Google Cloud connection is reached through its Google Cloud button.
