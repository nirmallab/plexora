# P6: the browser node against the product itself

Date: 2026-11-05. Record: `P6-M-2026-11-05.json`.

Verdict: **GO**.

## Question

For a local project on fast local disk, is the browser node within reach of today's product, which is the Python server and its page on the same machine? P1's viewer arms compared the browser feed with a Python *node* feeding the same minimal viewer. P6 puts the real app on the other side: its page, its boot, its own tile route and its own completion test.

## Set-up

- **Product arm.**
  - A scratch Plexora server (`tools/bench3d/serve.py`) runs on a bench data root that holds one project, `lsp11385`: the M image, its label pyramid and its 202,049-cell table, registered by `bench/p6_project.py` through `plexora.datasets.create_project`. It is never the user's data root.
  - `tools/bench_remote/tour.mjs` drives the page. That is the remote benchmark's own tour, with its completion test from `tourpage.js`: every visible channel fully loaded, at the finest level OpenSeadragon wants, as an HD source, for two polls after two redraws.
  - Passes: C1, with an empty browser cache, then C2, warm. Channels 0, 1 and 2. The z steps are skipped, because the image is 2-D (`tour.mjs` now skips them when it is given no z0).
- **Browser arm.**
  - The same steps, in the same order, from the same waypoints. Each move makes the same OpenSeadragon calls `tourpage.js`'s `place()` makes.
  - The pane is the product viewer's size, 1060 × 855 (measured on the product page).
  - The completion rule is `tourpage.js`'s own, ported: two redraws after the move, springs at rest, every item fully loaded, held for two polls 5 ms apart.
  - The springs are the product's (1.2 s, stiffness 6.5). The POC viewer otherwise turns animation off, which would make the animated steps incomparable.
  - "Revisit" runs the tour again in the same viewer, from the home view, beside the product's C2.
- **Waypoints:** the centroids of the cells at 30 %, 60 % and 85 % along X, so every one is on tissue.
- **Chrome:** both arms are headless on the GPU, with vsync on, as `tour.mjs` runs it.
- **Blocks:** in ABBA order (product, browser, browser, product). Per step, the mean of the two blocks of each arm; then the geometric mean of browser ÷ product over the navigation steps.
- **Open is not like for like.** The product's open counts from navigation: its page, its scripts and panels, the server's first reads, the first view. The browser's counts from creating the viewer with the file already picked, so the static page's own load is added to it in the verdict.
- **Memory:** the peak working set of each arm's renderer process. The product's is sampled every 0.5 s while `tour.mjs` runs.

- **Every step that needs new tiles is 2.4–3.3× faster in the browser** (ratios 0.30–0.41). The product's tiles come through Python (read, quantise, PNG-encode) and the network stack. The browser's come from geotiff.js workers reading the file directly.
- **Steps that need no new tiles are the same in both arms:** home, the revisit of a, and the two animated steps, which are the springs' own 1.2 s. They pull the geometric mean towards 1. Over the four tile-fetching steps alone it is 0.35.
- **Open:** the product's first open in a block includes the server's first reads of the file (3.3 s); its second, 1.2 s. The browser arm's 0.45 s plus its page's own 0.23 s load is a third of the product's mean.
- **Memory:** the product's renderer peaked at 1.3 GB, the browser arm's at 0.7 GB. The product page carries the whole app; the browser arm carries the minimal viewer (see below).

## What this does and does not show

- **It shows the data path.** Same image, same machine, same Chrome, same completion test: the browser reading its own file reaches full sooner than the product reading through Python, cold and on revisit.
- **It does not show the static app's boot.** The browser arm is the POC's minimal viewer, not the whole static build of the app (Phase 0–2). That build will carry the same scripts and panels the product page loads, so the product's open is the better guide to the static app's first paint; the browser node's data path then sits under it.
- **The two revisits are different things.** The product's C2 is a new navigation: its tiles are cacheable (`Cache-Control: private, max-age=31536000`), but every tile is fetched from the cache, decoded and uploaded again. The browser arm's revisit stays in the same viewer, so its tiles are already in OpenSeadragon's cache, as the product page's would be within one session. The like-for-like comparison is the cold pass.
