Date: 2026-11-05 (two rounds the same day; the records are the second round's). Records: `P2-M-2026-11-05.json`, `P2-L-2026-11-05.json`, `P2B-S-2026-11-05.json`, `P2B-M-2026-11-05.json`, and `P2B-M-2026-11-05-w4.json` / `-w8.json` (4 and 8 workers).

Verdicts:
- **P2: GO** on M and L.
- **P2b: GO** on S and M. The first round was PARTIAL, at 2.7× Python's time in one worker; band workers bring it to 0.44× (0.72× with 4 workers).

## P2: a prepared label pyramid through the GPU cell layer

**Question.** geotiff.js reads a label pyramid's uint32 ids from a local file. Can they go straight to the product's GPU cell layer (`labelGpu.js`, `label.frag.glsl`), drawing the same outlines as the node's label PNGs, with use case 2's live gate drag intact?

**Set-up.**
- The minimal viewer from P0, with one mask layer (outline mode, filled source) over the image channels.
- The ids and one marker column (CD45) come from the node's table routes, before anything is timed.
- The gate drag is 40 ticks of `evaluateGateMask` (the product's), then a gate-table upload, then a redraw. The time is measured from the change to two frames later.
- Blocks ran node, browser, browser, node, each in a fresh profile.
- **M:** LSP11385's mask pyramid (uint32, 52923 × 45381, 7 levels) and its 202,049-cell table, over two image channels.
- **L:** Orion CRC02's mask (int32, 48460 × 58709, 7 levels) and its 1,260,592-cell table, mask only.

**Results (Measured).**

| Fixture | Ids | Arm | View to full (ms) | Gate evaluate p50 (ms) | Drawn update p50 / p95 (ms) |
|---|---|---|---|---|---|
| M | 202,049 | node | 746, 743 | 0.7–0.9 | 18.6–18.7 / 19.7–19.9 |
| M | 202,049 | browser | 214, 209 | 0.6–0.7 | 18.3–18.5 / 19.1–19.7 |
| L | 1,260,592 | node | 387, 392 | 2.3–2.4 | 18.4 / 19.0–19.5 |
| L | 1,260,592 | browser | 163, 202 | 2.5–2.7 | 18.3–18.4 / 19.2–19.6 |

- **Label tiles:** 200/200 random tiles over every level are byte-identical between the two arms, on both fixtures. A uint32 id's little-endian bytes *are* the RGBA8 layout `data_model.read_tile` builds (alpha 0 below 2^24), so the browser node delivers them with no conversion at all.
- **The GPU cell layer was active in every block**, and all four blocks drew the same canvas (SHA-256 equal).
- **The drawn update** is the same in both arms, as it should be: once tiles are resident, the gate is the GPU's work. At 1.26 M ids it is 18.4 ms against a 30 ms bound. Use case 2's 25 ms was measured on the product page, at a different size.
- **The browser feed reaches full 2–3.5× sooner.**

## P2b: a flat mask turned into a pyramid in the browser

**Question.** Can a flat label mask be made into a label pyramid in the browser, into OPFS, without hurting the page? It has to be identical to the pyramid Python builds from the same file, and readable again after a restart.

**Set-up.**
- `page/src/workers/pyramidWorker.js` mirrors `segmentation_pyramid`'s FILLED mode (`page/src/lib/reduce.js`, tested exactly against Python's own arithmetic):
  - nearest-neighbour, so level L's pixel (y, x) is level 0's (y·2^L, x·2^L);
  - levels until one tile covers the image (`pyramid_factors`).
- **Band workers** (second round). The work is spread over `pyramidBandWorker.js` workers, 12 on this 24-thread machine by default.
  - A job is one band of level 0: a tile row and a run of four tiles. Each band worker opens the file itself, decodes its band and samples every coarser level's part of it.
  - The coordinator owns the OPFS files. It pastes parts into 1024² tiles, hands each finished tile to a band worker to deflate (`CompressionStream`, fed directly, not through a Blob), and appends it to the level's file through a sync access handle.
  - At most 128 MB of tiles wait for deflation; past that no band is read.
  - The same builder makes flat images into pyramids (P7).
- **Level 0 is not copied:** the viewer reads it from the user's own tiled file.
- **Python's reference:** `pyramidize_segmentation_mask(outline=False)` on the same file (`bench/truth_mask.py`), timed, then served by a node for a tile-by-tile comparison.
- **M:** LSP11385's mask level 0 written flat by `fixtures.py`: 52923 × 45381 uint32, 9.6 GB raw, 32 MB deflated. It is above Python's 8 GB whole-read budget, so Python streams too.
- **S:** exemplar-001's `cell.ome.tif` (3138 × 2511 int32). It turned out to be a pyramid already (two SubIFDs); the builder rebuilds from its level 0 and records the layout.

**Results (Measured).** The first round's single worker is shown for comparison (its record was replaced by the second round's).

| | S | M, 12 workers | M, 8 | M, 4 | M, first round (1 worker) |
|---|---|---|---|---|---|
| Build, wall (s) | 0.2 | **9.6** | 11.6 | 15.7 | 57.9 |
| Python's own conversion (s) | 0.13 | 21.8 | 21.8 | 21.8 | 21.8 |
| Build / Python | — | **0.44** | 0.53 | 0.72 | 2.7 |
| Main-thread long tasks > 50 ms during the build | 0 | 0 | 0 | 0 | 0 |
| Page frame rate during the build | 62 | 58 | 57 | 58 | 57 |
| Peak renderer working set | 0.24 GB | 1.66 GB | 1.14 GB | 0.75 GB | 1.09 GB |
| Derived levels in OPFS (deflated) | 0.3 MB | 20.2 MB (raw would be 3.2 GB) | 20.2 MB | 20.2 MB | 20.2 MB |
| 200 derived tiles identical to Python's | 200/200 | 200/200 | 200/200 | 200/200 | 200/200 |
| First tile after a relaunch (ms) | 15 | 19 | 15 | 15 | 15 |

- **A whole-slide mask is not "beyond a browser tab"** (investigation §5.2 predicted it was).
- **The browser now builds it in under half of Python's time.** The first round's single worker spent three quarters of its 58 s decoding level 0; spread over band workers that cost divides by the worker count. Four workers already beat Python, in 0.75 GB.
- **Memory follows the worker count:** about 0.13 GB a worker on top of the coordinator. A machine with fewer cores gets fewer workers, and so less memory, by default.

**Storage.** The first round read Chrome's `estimate()` quota of about 10.7 GB as a limit. It is not one: Chrome reports usage plus 10 GiB (P7, "Storage").
