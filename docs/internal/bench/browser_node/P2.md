# P2 and P2b: label masks in the browser node

Date: 2026-11-05. Records: `P2-M-2026-11-05.json`, `P2-L-2026-11-05.json`, `P2B-S-2026-11-05.json` and `P2B-M-2026-11-05.json`.

Verdicts:
- **P2: GO** on M and L.
- **P2b: PARTIAL.** Every GO threshold passes except the hypothesis "within 2× of Python's own conversion" (2.7× on M).

## P2: a prepared label pyramid through the GPU cell layer

**Question.** geotiff.js reads a label pyramid's uint32 ids from a local file. Can they go straight to the product's GPU cell layer (`labelGpu.js`, `label.frag.glsl`), drawing the same outlines as the node's label PNGs, with use case 2's live gate drag intact?

**Set-up.**
- The minimal viewer from P0, with one mask layer (outline mode, filled source) over the image channels.
- The ids and one marker column (CD45) come from the node's table routes, before anything is timed.
- The gate drag is 40 ticks of `evaluateGateMask` (the product's), then a gate-table upload, then a redraw. The time is measured from the change to two frames later.
- Blocks ran node, browser, browser, node, each in a fresh profile.
- **M:** LSP11385's mask pyramid (uint32, 52923 × 45381, 7 levels) and its 202,049-cell table, over two image channels.
- **L:** Orion CRC02's mask (int32, 48460 × 58709, 7 levels) and its 1,260,592-cell table, mask only.

**Results (Measured).**

| Fixture | Ids | Arm | View to full (ms) | Gate evaluate p50 (ms) | Drawn update p50 / p95 (ms) |
|---|---|---|---|---|---|
| M | 202,049 | node | 702, 736 | 0.6–0.7 | 18.5–18.7 / 19.3–19.5 |
| M | 202,049 | browser | 270, 272 | 0.6–0.7 | 18.2–18.3 / 18.9–19.0 |
| L | 1,260,592 | node | 449, 417 | 2.3–2.4 | 18.2 / 19.1–19.4 |
| L | 1,260,592 | browser | 212, 220 | 2.5–2.8 | 18.6–18.8 / 19.5–19.7 |

- **Label tiles:** 200/200 random tiles over every level are byte-identical between the two arms, on both fixtures. A uint32 id's little-endian bytes *are* the RGBA8 layout `data_model.read_tile` builds (alpha 0 below 2^24), so the browser node delivers them with no conversion at all.
- **The GPU cell layer was active in every block**, and all four blocks drew the same canvas (SHA-256 equal).
- **The drawn update** is the same in both arms, as it should be: once tiles are resident, the gate is the GPU's work. At 1.26 M ids it is 18.6 ms against a 30 ms bound. Use case 2's 25 ms was measured on the product page, at a different size.
- **The browser feed reaches full 2–2.7× sooner.**

## P2b: a flat mask turned into a pyramid in the browser

**Question.** Can a flat label mask be made into a label pyramid in a worker, into OPFS, without hurting the page? It has to be identical to the pyramid Python builds from the same file, and readable again after a restart.

**Set-up.**
- `page/src/workers/pyramidWorker.js` mirrors `segmentation_pyramid`'s FILLED mode:
  - nearest-neighbour, so level L's pixel (y, x) is level 0's (y·2^L, x·2^L);
  - levels until one tile covers the image (`pyramid_factors`).
- Level 0 is read one tile row at a time. Every coarser level samples that band, and each full tile row of a level is deflated (`CompressionStream`) and appended to that level's OPFS file through a sync access handle.
- **Level 0 is not copied:** the viewer reads it from the user's own tiled file.
- **Python's reference:** `pyramidize_segmentation_mask(outline=False)` on the same file (`bench/truth_mask.py`), timed, then served by a node for a tile-by-tile comparison.
- **M:** LSP11385's mask level 0 written flat by `fixtures.py`: 52923 × 45381 uint32, 9.6 GB raw, 32 MB deflated. It is above Python's 8 GB whole-read budget, so Python streams too.
- **S:** exemplar-001's `cell.ome.tif` (3138 × 2511 int32).

**Results (Measured).**

| | S | M |
|---|---|---|
| Build, wall (s) | 0.30 | **57.9** |
| … reading level 0 (s) | 0.18 | 42.6 |
| … deflating (s) | 0.05 | 12.2 |
| … sampling (s) | 0.01 | 2.2 |
| Python's own conversion (s) | 0.13 | 21.8 |
| Main-thread long tasks > 50 ms during the build | 0 | 0 |
| Page frame rate during the build | 60 | 57 |
| Peak renderer working set | 0.21 GB | 1.09 GB |
| Derived levels in OPFS (deflated) | 0.33 MB | 20.2 MB (raw would be 3.2 GB) |
| Derived / source file | 0.01 | 0.63 |
| 200 derived tiles identical to Python's | 200/200 | 200/200 |
| First tile after a relaunch (ms) | 14 | 15 |

- **A whole-slide mask is not "beyond a browser tab"** (investigation §5.2 predicted it was). The streaming builder holds one band, peaks at 1.09 GB and never blocks the page.
- **It is 2.7× slower than Python.** Python compresses on many threads; the worker reads and deflates on one. Three quarters of the time is decoding level 0 in one worker. Reading bands in several workers is the obvious next step and was not tried.

**Storage (Measured).** `navigator.storage.estimate()` in these fresh headless profiles reports a quota of about **10.7 GB**, on a 1.9 TB disk with 330 GB free. That is far below the "60 % of disk" the platform notes give. Raw derived levels (3.2 GB) would fit, but a few masks would not; deflated (20 MB) they always do. Whether a user's ordinary profile gets more is not measured here (open item).
