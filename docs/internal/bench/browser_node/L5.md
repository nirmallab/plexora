# L5: Plexora's numba kernels as a compiled package (plexora-kernels)

Date: 2026-11-07. Plan item L5, design decision D7. Branch `web/kernels`.
Records:
- `L5-desktop-2026-11-07.json`: every kernel on this machine as Python, numba (warm and cold) and the Cython port; four product operations; start-up.
- `L5-web-2026-11-07.json`: every kernel in the website's worker, as the WebAssembly port and as the Python the website ran before; the same four operations.

Machine: i9-12900K, 128 GB, Windows 11 25H2. Desktop: CPython 3.13.15, numpy 2.5.2, numba 0.67.0. Website: Chrome 156 (headless), Pyodide 314.0.7 (Python 3.14.2, numpy 2.4.6).

**Verdict: GO.** Every kernel is ported (22 `@njit` kernels and TIFF LZW). Each port equals numba bit for bit on the desktop. On the website the port is about as fast as native numba: median 1.18×, at worst 2.25×. Against the Python the website ran before, it is 97–1,395× faster (median 340×). The plan expected 2–4× numba and 10–50× Python. The desktop no longer pays numba's LLVM compile: 11.6 s on a first start, 2.0 s on every start after.

## What was asked

D7: Plexora's numba kernels become `plexora-kernels`, written in Cython and built as wheels for Windows, macOS, Linux and Pyodide. `jit.py` uses it first, then numba, then plain Python.

On the website there is no numba. Today every `@njit` there runs as plain Python, through an identity stub.

## The package

It lives in `kernels/` as its own distribution:
- name `plexora-kernels` 0.1.0, import name `plexora_kernels`, with its own `pyproject.toml` and version;
- one extension, `src/plexora_kernels/_kernels.pyx`, which includes `planes.pxi`, `points.pxi`, `surfaces.pxi` and `lzw.pxi`.

It is not `plexora/_kernels/`, as the plan's file list suggested, for two reasons:
- Plexora's wheel stays pure (`py3-none-any`). The website ships it as one, and `build.py` builds it with `pip wheel`.
- A `plexora._kernels` installed into site-packages is shadowed by the source tree in every development checkout. `plexora` is a regular package and resolves to the checkout.

`MANIFEST.in` prunes `kernels/` from Plexora's sdist.

Each port has the name, arguments and results of the kernel it ports. `KERNELS` maps `"module.name"` to the port.

Before it runs, a port checks what it was handed: dtypes, dimensions, writability and scalar kinds. Each port is built for the dtypes the product passes:
- the outlines and boxes take any of the 8 integer dtypes;
- the rest take the fixed dtypes their wrappers convert to (`uint32` labels, `float32` planes, `float64`/`int64` arrays).

A call a port was not built for runs the **fallback** Plexora sets: the kernel through numba where numba exists, otherwise as Python. `FALLBACK_CALLS` counts these calls. The product never makes one (tested).

A port also raises `IndexError` where numba would write out of bounds. Examples: a label past its per-label arrays, or more pairs than were counted.

The loops run without the GIL, matching numba's `nogil=True`.

Build flags:
- `-O3 -ffp-contract=off`, so no compiler fuses `a*b + c` into an FMA. numba's LLVM does not fuse without fastmath.
- Under Pyodide, `[tool.pyodide.build]` sets `-O3` for compiling and for wasm-opt, instead of Pyodide's `-Oz`. It is 30 kB larger, and the worker's `nets._count` falls from 12.7 to 4.6 ms (`link_Oz_compiled_best_ms` in the web record).

Each port follows its kernel's arithmetic step by step:
- the same operations in the same order and precision (a float32 sum stays float32 where numba's does);
- numba's `math.expm1` on float32 is `expm1f`, so the port calls `expm1f`;
- float `//` is CPython's `float_divmod`, as numba's is;
- `np.percentile` is numba's own algorithm: the same select-two and the same interpolation.

## How Plexora chooses (`plexora/server/utils/jit.py`)

`njit` hands out the first of these:
1. the port;
2. `numba.njit`;
3. the function itself.

A module's kernels come from the package **only while every kernel in that module still has the source it was ported from**. The rule is all or nothing per module, because a numba kernel cannot call a compiled port.

The check uses fingerprints:
- A fingerprint is a kernel's tokens, without comments, layout or docstring. It is the same under 3.12, 3.13 and 3.14.
- `kernels/tools/fingerprints.py` records them in `_fingerprints.py`, together with the commit they were read from.
- On the desktop, jit.py reads the module's source at import. A stale module goes back to numba, with one warning.
- The website ships sourceless bytecode, so the website's build checks the fingerprints instead (below).

Other parts of the switch:
- `PLEXORA_KERNELS=0` switches the package off. It is documented in `env_vars.yaml` and the generated page.
- `PLEXORA_NO_NUMBA=1` still switches numba off. With the package installed, the kernels then stay compiled.
- `jit.enabled()` is true for either route.
- `jit.is_compiled(fn)` and `jit.implementation(fn)` (`compiled`, `numba` or `python`) say which route a kernel took. `label_overlay` and `cell_features` now ask about their own kernel rather than whether numba is present.

**Changing an `@njit` kernel now means changing its port too.** Edit the `.pxi`, run `kernels/tools/fingerprints.py`, rebuild, then run `tests/test_kernels_package.py`. That test fails on a stale fingerprint. `SKILL.md` says so.

## Agreement: the rule and what was found

`tests/kernel_cases.py` builds one case per kernel, 27 cases in all: some kernels get a second dtype or variant. It uses numpy only, with uniform draws and `+ - * / sqrt`, so the inputs are the same bits on every platform. There are no sin, log or normal draws, whose last bits differ between C libraries and numpy's SIMD paths.

`tests/test_kernels_package.py` runs every case in three fresh interpreters:
- the port;
- numba (`PLEXORA_KERNELS=0`);
- the Python (`PLEXORA_NO_NUMBA=1` as well).

It compares every result and every array the kernel wrote.

- **Port and numba: identical, bit for bit**, floats included, on all 27 cases. The rule allows 1e-12 for `segqc.label_stats`'s `excess`, which calls the C library's `expm1f`. On this machine it was exact anyway.
- **Port and Python:** every integer output is identical. Floats agree to 2.6e-8 at most:
  - `label_stats`' `excess`: the Python calls double-precision `math.expm1`;
  - `_background_blocks`: 2.2e-16 from numpy's percentile interpolation.

  The rule is 1e-6 relative.
- **Website and desktop** (`tests/test_browser_kernels.py`, Chrome): the inputs are the same bits. The website's WebAssembly port equals the desktop's port on 26 of 27 cases, and so equals numba. The exception is `label_stats`' `excess`, at 4.5e-8 relative: WebAssembly's `expm1f` comes from musl, the desktop's from UCRT.
- **The product** (one probe calls every product path through its public function):
  - every kernel runs compiled, with no fallback;
  - numba is never imported;
  - switched off, the kernels are numba again;
  - handed int64 labels, a uint32-only port runs numba and gets numba's answer;
  - a port of older code is not used for its whole module.
- **Whole operations agree.** The surface mesh of a 32×256×256 block is the same bytes compiled, under numba, as Python, and on the website. The same holds for segmentation QC's sums and pairs and for the neighbour counts.

Existing tests changed:
- the "plain" side of `test_autogate_units` and `test_segmentation_qc`'s two-way test also sets `PLEXORA_KERNELS=0`;
- `test_imagecodecs_shim` checks both LZW decoders against imagecodecs.

`test_surface_engine`'s interpreted-vs-compiled test works unchanged: ports carry `py_func`.

## The website

- **The bundle.** `plexora/browser/stages.py` gives the base stage a `platform` list, `["plexora-kernels"]`. The wheel is 98 kB brotli on the first visit.
- **The build.** `tools/browser_build/build.py` takes the wheel from `--kernels-wheel`, `PLEXORA_KERNELS_WHEEL` or the newest in `kernels/dist/`. It refuses:
  - a wheel for another Pyodide (the tag must be `cp314-…-pyemscripten_<lock abi>_wasm32`);
  - a wheel whose recorded fingerprints differ from this checkout's kernels.

  It writes `{wheel, ported_from, fingerprints}` into `manifest.json`, so `--plexora-only`, which keeps or replaces the wheel, re-checks a bundled wheel against a changed checkout.

  A full build with no wheel stops, unless given `--no-kernels`.
- **CI.** `web.yml`'s bundle job and `release.yml`'s web job build the wheel first with `uvx --from cibuildwheel==4.3.5 cibuildwheel --platform pyodide`.
- **Loading.** The worker's `unpackArchive` puts the `.so` in site-packages. The app's boot imports a kernel module, so the package is loaded at boot. Compiling and linking the module costs about 3 ms (2.4–3.9 ms timed under Node's V8).
- **Ready time.** 12 runs, ABBA, of the same bundle with and without the wheel. The paired difference (with − without) had a median of +0.01 s and a mean of +0.18 s. That is inside the run-to-run noise: ready time went from 9.0 to 13.7 s over the session, with other work running on this machine. No cost is measurable.
- **Proof.** `tests/browser/kernels.mjs` and `tests/test_browser_kernels.py`, as in the agreement section.

## What is left, and decided against

- **Not run:** `kernels.yml` (macOS, aarch64 and MSVC builds) and the CI steps in `web.yml` and `release.yml`. CI's Windows wheels are MSVC (`/O2 /fp:precise`), not llvm-mingw. The agreement job is what proves they match numba.
- **Plexora does not depend on plexora-kernels yet.** The desktop app's bundled runtime (`scripts/release.py`) does not install it, and `pyproject.toml` has no extra for it. Until it ships there, the desktop keeps numba's warm-up. Adding it is a release decision; numba stays a core dependency as the fallback.
- **Not published.** Publishing to PyPI is the user's call (below). The licence in `kernels/pyproject.toml` is Plexora's EULA (`LicenseRef-Plexora-EULA-1.0`, `kernels/LICENSE` points at it). Confirm that before publishing.
- **WebAssembly SIMD (`-msimd128`) is not enabled.** It would narrow Safari to 16.4+. The ports are already about numba's speed.
- **The Pyodide tag re-rolls per Pyodide ABI.** A new `PYODIDE` in `build.py` needs a rebuilt wheel, and build.py refuses an old one.
- **Not ported:** nothing. A future `@njit` kernel in a new module simply runs through numba or Python until it is ported.

## Releasing (the user's call; nothing here publishes)

1. Change the ports with their kernels, run `python kernels/tools/fingerprints.py`, and bump `version` in `kernels/pyproject.toml` and `__version__` in `src/plexora_kernels/__init__.py`.
2. Run `kernels.yml` by hand (workflow_dispatch). It builds every wheel and the sdist and holds them to numba.
3. Publish the artifacts with a PyPI token: `uv publish dist/*`, as for spatialbridge. PyPI accepts PEP 783 `pyemscripten` tags. The first upload reserves the name `plexora-kernels`.
4. To ship it with the desktop app, add it to Plexora's dependencies or to the bundled runtime. The website's bundle takes the Pyodide wheel at build time, so no release is needed there.

## Traps met

- **Generator draws are not the same bits everywhere.** numpy's `normal` and `gamma` draws, and `sin`, `log1p`, differ in the last bits between this machine's SIMD paths and WebAssembly. The cross-platform inputs use uniform draws, a rational circle and `sqrt` only.
- **`np.asarray(5)` is int32 on wasm32.** Hash Python ints by value.
- **Negative indices.** A module compiled with `wraparound=False` turns `obj[-1]` on a Python object into a wrong index (`IndexError: index -1598`). Use explicit lengths.
- **Link flags.** Pyodide links side modules at `-Oz`, and `extra_link_args` do not override it. Use `[tool.pyodide.build] ldflags`, with `pyodide build` run from the package's directory.
- **The bundle's copy of the wheel is sourceless.** `_fingerprints.pyc` was compiled for 3.14 and cannot be read by the 3.13 that runs the build. The manifest keeps the fingerprints instead.
- **Test inputs.** A test LZW encoder must raise its code width when the next code reaches 2^w, as libtiff's encoder does. The decoder's "early change" (2^w − 1) is the other side of the same rule.
- **pytest ids.** A pytest id made from a 50 kB bytes parameter overflows Windows' 32,767-character environment variable (`PYTEST_CURRENT_TEST`). Name the cases.
