# P9: Plexora's AI layer in the browser (Pyodide)

Date: 2026-11-06. Records:
- `P9-P9S-2026-11-06.json`: the Pyodide release as published.
- `P9-P9S-2026-11-06-trimmed.json`: the precompiled, brotli build.
- `P9-P9S-2026-11-06-pages.json`: the precompiled build as Cloudflare Pages can serve it.
- `P9-P9S-2026-11-06-metacache.json`: a product change, prototyped on both sides.

Verdict: **PARTIAL** for every build; no STOP condition met.

- **Met:** the same code gives the same answers at about CPython's speed. Packets, answers, final states and gates are identical, and the session takes 0.9–1.2× CPython's time. The viewer is not slowed.
- **Missed:** startup. The AI tools are ready 6.2–7.1 s after a visit on this machine; the bar for a return visit is 3 s. A first visit over 50 Mbps / 20 ms takes 13.8 s at best; the bar is 10 s.

## Question

The website must open and work with nothing installed, and still be AI-native: the same Python AI layer the desktop app, MCP and the SCIMAP Pro bridge use. Can that layer run unchanged in the browser, in Pyodide beside the viewer? Or does the website need a small download beside the browser?

The user's bars (2026-11-06):
- AI tools greyed for at most 10 s on a first visit (50 Mbps / 20 ms), and at most 3 s on a return visit.
- The viewer never waits on Python.
- A gating session takes at most 2× CPython's time.
- Correctness: the same gates and packets as CPython.

## Set-up

- **Runtime.** Pyodide 314.0.7 (Python 3.14.2) in a module worker, `page/src/workers/pyWorker.js`. It boots when the page loads. Everything is served from the page's own origin, `serve_static.py --pyodide`:
  - the release (`bench/p9_dist.py`);
  - the Plexora wheel built from this checkout, without its web client (13 → 3.7 MB);
  - the pure-Python wheels Pyodide does not ship (spatialagents, spatialbridge, biocognia, biocognia-markers, tifffile, ome-types and its deps, flask and its deps). They are unpacked straight into site-packages, with no micropip.
- **Packages loaded** (`page/py/p9_packages.json`): what the session imports, read from `sys.modules` after a session.
  - **Left out, because the session never imports them:** opencv, h5py, shapely and anndata.
  - **Left out of the trimmed build:** pandas. pyarrow declares it, and scikit-learn imports it when it is present (`sklearn.utils.fixes`).
- **"Ready"**: every gating module imported and `registry.discover(["gating"])` done (150 capabilities). From then on the AI tools could be enabled. Times run from the page's navigation start.
- **Builds:**
  - **as published:** the release's packages, which ship `.py` sources only.
  - **trimmed** (`p9_dist.py --variant pyc`, then `pycbr`):
    - every module precompiled to sourceless bytecode for Pyodide's Python (unchecked-hash `.pyc`, compiled with CPython 3.14.7);
    - pandas dropped from pyarrow's declared dependencies;
    - wheels stored and served with brotli (`Content-Encoding: br`, over https);
    - pyarrow fetched at the first Parquet call rather than at boot (`lazy`).
  - **pages:** the precompiled wheels deflated, as they come. Only the core's wasm and JavaScript are brotli'd, as Cloudflare compresses on the fly. Pages takes no file over 25 MiB, and the stored polars wheel is 110 MB.
- **Substitutions** (`page/py/p9_boot.py`): 8 functions, at most 19 lines of code each and 111 in all. None alters a packet, gate, state or provenance entry; the comparison checks that.

| Shim | Lines of code | Stands in for |
|---|---|---|
| `stub_root` | 13 | `plexora/__init__.py` builds the Flask app at import; the gating path needs the package path, `__version__` and `get_config` |
| `zlib_for_zlibng` | 9 | `server/utils/fast_png.py` imports imagecodecs (no wasm build) for one call, `zlibng_encode` |
| `deferred_threads` | 18 | no threads: a started thread runs where its starter yields (join, sleep, Event wait) |
| `jobs_between_calls` | 14 | a job queued by a capability call (the classifier) runs when the call returns, as an idle worker would run it |
| `sync_executor` | 14 | `ThreadPoolExecutor` (autogate/bulk.py, evidence/crops.py) runs each call on submit |
| `yielding_sleep` | 11 | a poll's `time.sleep` yields to queued jobs; never waits |
| `parquet_by_pyarrow` | 19 | Pyodide's polars is built without Parquet; the gate store (api/store.py) reads and writes it. pyarrow does, fetched on first use through JSPI's `run_sync` |
| `licence` | 13 | a throwaway issuer as tests/conftest.py mints one; Pyodide's `os` has no `link`, so biocognia's exclusive create takes its own `OSError` fallback |

- **Data.** The user's picked files are mounted with WORKERFS: read on demand, never copied. The project's config names them.
  - **Images and masks:** the product's own local readers (tifffile) run on them unchanged. The worker reads picked files in 1 MiB blocks, keeping the last 64. Without that, WORKERFS makes one ~0.45 ms `FileReaderSync` slice per `read()`, and the M session made 31,177 reads.
  - **Tables:** copied into MEMFS, because polars memory-maps what it reads and a WORKERFS file cannot be mapped.
  - **Large tables:** come from the page's column store (P3) as Float64 columns. polars in Pyodide cannot parse a large CSV: its reader panics, "could not spawn threads".
- **The session.** It is `tests/test_gating_session.py`'s oracle session, unchanged (`page/py/p9_oracle.py`): engine v1, the defaults, `answer_review`, then `drive` to the end.
  - Both sides wait for the session's background job (the classifier) before reading the final state, as the suite's `_finish_agent_jobs` does.
  - **Fixtures** (`bench/p9_fixture.py`, `tests/autogate_fixtures.make_gating_project`):
    - **S:** grid 16, 768 px, 3 markers, 256 cells;
    - **M:** the suite's own oracle test, grid 32, 1280 px, 5 markers (CD3, CD8, CD20, CD4, FOXP3), 1024 cells.
- **Reference.** The same `p9_run.py` in the conda env: CPython 3.13, real threads, numba, the full Plexora package. Three runs per fixture, each in its own process on a fresh data root; the median is used (`bench/truth_p9.py`). The three CPython runs are identical to each other in every record.
- **Rules** (`bench/compare_p9.py`):
  - **hard:** packet kinds in order; every packet's JSON and the Oracle's answer, floats within rtol 1e-6; final unit states and gates;
  - **soft:** images within 2 levels (pixels, not bytes, because zlib and zlib-ng differ); `get_all_gates` equal.
- **Arms** (`bench/p9.mjs`):
  - **cold:** fresh profile, boot to ready, then the S session.
  - **return:** the same profile and port, relaunched.
  - **throttled:** fresh profile; every response over one shared 50 Mbps link after a 20 ms round trip (`serve_static.py --throttle`, server side, so the worker's fetches are throttled too).
  - **viewer:** ABAB × 4, a fresh profile each. The S image (P1's) is opened and panned with the worker booting beside it and without, recording main-thread long tasks.
  - **M:** cold boot and the M session.
  - **L:** 1.26 M × 29 cells handed to Python.
- **Machine:** the bench machine (i9-12900K, 24 threads, 128 GB), Chrome 156 headless on the GPU. A laptop is slower, and startup scales with CPU.

- **Precompiling cut imports from 7.2 s to about 2 s.** Leaving pyarrow (and the pandas it declared) out of the boot cut package loading from 5.9 s to 2.6 s.
- **The first visit is bound by bytes.** 46 MB over 50 Mbps is 7.4 s before any CPU. The core must arrive before packages are requested.

## Found on the way

The comparison caught each of these, as a packet, a state or a gate that differed from CPython's:
- **A missing pure-Python wheel changed a packet with no error.** ome-types needs `pydantic_extra_types`, and `pixel_scale.pixel_size` swallows the ImportError. The project read as uncalibrated, and the session asked a `pixel_setup` question CPython never asked.
- **A thread run inside its starter's call broke the session record.** The bulk pass, run inline inside `gating_session_start`, saved the session record, and `gating_session_start` then wrote its stale copy over it. Threads now run where the starter yields.
- **A failed bulk pass looked like the user's gates.** When pyarrow's own dependency was missing, the first bulk pass failed after writing gates, and the resumed pass read them as "your gate kept" (`skipped_manual`) for every marker.
- **The classifier job is asynchronous in CPython.** The final state is therefore read only after background jobs settle, on both sides.
- **The M session re-reads one TIFF header about 400 times, on CPython too.** Most of the calls are QC's input fingerprints asking `pixel_scale.pixel_size` per cell-exclusion check; `brightfield.is_rgb_layout` does the same. Under CPython's profiler those reads take 6 s or more of a 17.5 s run (`is_rgb_layout` is also called inside `pixel_size`). Caching both readers per (path, size, mtime) takes the CPython M session from 13.4 to 10.7 s and Pyodide's from 16.4 to 12.9 s, with identical results (the metacache record).

## Required product changes

A browser build needs these. None changes what the desktop app or the server computes. Each lands with tests, and the desktop's behaviour is checked against them.

1. `plexora/__init__.py`: build the Flask app lazily (`plexora.app` through the module `__getattr__`), so a headless import pays nothing for it.
2. `server/utils/fast_png.py`: fall back to `zlib` when imagecodecs is absent.
3. `agent/jobs.py`, `autogate/bulk.py`, `evidence/crops.py`: a job runner and an executor that a worker without threads can supply (queued, run when idle).
4. `api/store.py`'s Parquet: either through pyarrow in the browser, or a format both builds of polars write (Arrow IPC), read back as either. That is a product decision.
5. biocognia's `store.create_private_json`: treat a missing `os.link` as its `OSError` fallback (a biocognia release).
6. `pixel_scale.pixel_size` and `brightfield.is_rgb_layout`: cache per (path, size, mtime). This is worth doing for the desktop on its own (−20 % on the M session).
7. Silent fallbacks: log what `pixel_size` swallows, and add a CI import check of the browser's wheel set.
8. The browser's table provider takes columns from the JavaScript column store. polars in wasm cannot parse a large CSV.
9. The browser build itself: precompiled bytecode, Plexora's Python without its web client, no pandas, pyarrow on demand.

## Hosting on viewer.plexoraapp.com

- **Cost.** Static files only, with nothing per user on BioCognia's side. The site serves Pyodide and the wheels from its own origin with long-lived, versioned, immutable cache headers.
- **Cloudflare Pages:**
  - It holds no file over 25 MiB. The trimmed build's stored polars wheel is 110 MB, so Pages serves the "pages" build: 70 MB on a first visit, 17.3 s at 50 Mbps.
  - The 46 MB build needs a host that sends precompressed brotli as it is, such as R2 behind a Worker. Workers requests are billed beyond the free tier.
  - Pages does not reliably serve a `.br` through `_headers`.
- **The origin.** viewer.plexoraapp.com is its own origin, so its OPFS, IndexedDB and HTTP cache are its own. It is the same site as plexoraapp.com, so the two share Chrome's cache partition. The marketing site could warm the cache, but only after an explicit "open the viewer", never on every visit (46–70 MB).
- **Headers.** P9 needs no COOP/COEP (no SharedArrayBuffer).
- **Nodes and services.** Nodes allow the viewer's origin (`--allow-origin https://viewer.plexoraapp.com`), with Chrome's Local Network Access prompt as P5 measured. The analytics Worker must allow the origin too.
- **The current apps** (desktop, the Python server, the marketing site, analytics) are untouched by this proof. Nothing under `plexora/`, `website/`, `backend/` or `desktop/` changed.

## What this does and does not show

- **It shows** that the gating session's Python runs in a browser worker:
  - unchanged, apart from eight small substitutions for what Pyodide lacks (threads, imagecodecs, Parquet in polars, `os.link`);
  - with the same packets, answers, states and gates as CPython;
  - at CPython's speed or close, on CPython 3.13 with numba against Pyodide 3.14 with older numpy, scipy, scikit-learn and polars;
  - without slowing the viewer's main thread.
- **It does not show:**
  - **Other paths:** the in-app gateway (model calls), chat, QC, MCP or the SCIMAP Pro bridge in the browser. None was run.
  - **Other browsers and machines:** Safari, Firefox, or a slower machine.
  - **A real licence in the browser:** that is open question 8.
  - **Engine v3:** the session ran engine v1, as the suite's oracle test does.
- **Startup is the remaining gap, and none of these was measured:**
  - **Faster loading:** fetching packages while the core starts, or staged readiness (chat and the viewer's AI before gating's scikit-learn).
  - **Pyodide memory snapshots:** today they cannot restore dynamically loaded `.so` files, so a snapshot taken after scipy and polars load would not restore.
  - **A smaller package set:** gating without scipy and scikit-learn would be a semantic change.

## Consequence

This is not a STOP, so by the rule agreed before the proof the fallback, the small download beside the browser, is not triggered. The AI layer can stay one Python codebase for the desktop app, the cluster node and the website. What the proof leaves to decide is startup:
- **Accept** AI tools that become ready about 7 s after the page opens (on this machine), and about 14 s on a first visit at 50 Mbps, while the viewer works at once.
- **Or** fund the startup work above and measure it against the same bars.
