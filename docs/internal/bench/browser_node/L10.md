# L10: Video Studio's exports on the website

Date: 2026-11-07. Plan item L10. Branch `web/video`.

Record: `L10-2026-11-07.json`. It holds both runs below, each with what the driver saw and what the checker found.

Harness:
- `tests/browser/video.mjs` is the driver.
- `tests/browser/video_check.py` opens and compares the files.
- `tests/test_browser_video.py` is the pytest wrapper.

Machine: i9-12900K, 128 GB, RTX 3080, Windows 11; headless Chrome 156.0.8078.76.

The two arms:
- **Desktop:** CPython 3.13 Plexora with the desktop's own FFmpeg: `7.1-essentials_build-www.gyan.dev`, from imageio-ffmpeg 0.6.0 as `uv.lock` pins it, via `PLEXORA_FFMPEG`.
- **Website:** the static site with the website's Python bundle (Pyodide 314.0.7).

**Verdict: four of five formats work on the website. ProRes hands off to the desktop app.** MP4, WebM, GIF and PNG frames export on the website from the real panel.

With the same scene, the website's files are the desktop's:
- **MP4, WebM and PNG frames:** identical frame for frame. The WebM is identical byte for byte.
- **GIF:** within 1.3–1.6 of 255 per channel, mean absolute difference.

ProRes cannot be written on the website, because no LGPL build of FFmpeg for the web can encode it. The Export dialog shows the website's hand-off notice instead: "ProRes is in the desktop app", with Open Desktop App and Get the Desktop App. Building that LGPL FFmpeg ourselves needs Emscripten, which this session was not permitted to install. The recipe is below.

## What the website did before (measured, `--arms website`, 320 x 180)

| Format | Before | Why |
|---|---|---|
| MP4 (H.264) | a file, every frame black, a "50 nm" scale bar | The panel captured its starting scene before the viewer had its image. On the website, Python answers the panel's state before the page's node has opened the image. `viewerScene.currentViewport` then answers a 1-pixel rectangle, so every frame was 1/1024 of the image wide. |
| WebM (VP9) | the same | the same |
| ProRes (MOV) | disabled: "Needs ffmpeg on the server (pip install 'plexora[video]')." | The server's encoder report was the desktop's. Its advice cannot be followed on a web page. |
| GIF | a 605-byte file holding the site's home page, saved as `.gif` | Pillow wrote the GIF correctly in the page's Python. But the Download link pointed at a route the site does not serve, and a link cannot reach the page's Python. |
| PNG frames (zip) | the same 605-byte home page, saved as `.zip` | the same |

## What changed

- **The starting scene.**
  - The panel now waits for the viewer's image before it captures the starting scene (`whenImageOpen`, at most 15 s).
  - A capture with no image keeps no viewport, so the preset fits the whole image.
  - This applies to the desktop too.
- **Files the page's Python writes.**
  - `ServerEncoder.finish` reads the finished file through the page's fetch. It then saves the file as a download, as the browser encoders do. The export is recorded once.
  - The website is no longer treated as a remote server. Frames reach its Python as raw RGBA, not PNG.
  - The dialog says "in this browser" for these formats.
- **The encoder seam** (`encode_jobs.encoder()`, as the plan names it):
  - On the desktop and every server it is `ProcessEncoder`: `encoders.report()` and `writers.open_writer` as before. **The desktop's FFmpeg path is unchanged.**
  - In a web page it is `PageEncoder`. Its report probes no program. It offers PNG frames and Pillow's GIF. It leaves MP4 and WebM to WebCodecs. It answers ProRes with the hand-off notice. It refuses any writer a page cannot run.
- **ProRes on the website.**
  - The notice is `plexora/browser/routes.py` `FEATURES["video_studio.prores"]`. It is held to the same rules as the route notices (`tests/test_handoff_routes.py`).
  - The website's encoder report carries the notice, and the dialog draws it with `services/handoff.js`.
  - An agent's ProRes export on the website is refused with the notice. It is not quietly swapped for MP4.
- **The website's GIF** is written in the browser, frame by frame, in a worker (`static/videoGifWorker.js`, Plexora's own code). Each frame is encoded this way:
  1. It gets a 256-colour palette by median cut over a 5-bit histogram.
  2. It goes through an 8 x 8 Bayer dither, the classic order, as the desktop's `paletteuse=dither=bayer`.
  3. It is coded with GIF89a LZW.

  The GIF loops, and its delays are rounded so they add up to the video's length. Nothing but the file is held, so it is as long and as large as the desktop's. It is offered only on the website; the desktop keeps FFmpeg's.
- **Pillow's GIF** still exists in both apps. It holds every frame, so it is capped at 300 frames and 960 px. The cap is now in its report row (`limits`), so the dialog says "At most 960 px on the longer side here." before rendering, instead of failing at frame 301.

## Found on the way (not Video Studio's)

**The two apps open the same image at different channel levels.** The website's DNA opened at 0–65536 and the desktop auto-levelled it to 30113–59995. A video made from the viewer as it opens would therefore differ between the apps. The driver fixes the windows so the comparison measures the export alone. The levels are the viewer's (the page's channel stats on the website, Python's on the desktop) and want their own look.

## FFmpeg for the web: the facts for counsel (to be confirmed by counsel)

**Nothing from FFmpeg ships with the website.** No FFmpeg code, wasm or binary is in this branch or loaded by the page. The desktop's FFmpeg is unchanged: a GPL binary, run as a separate process (`THIRD_PARTY_NOTICES.md`).

The candidates, as published on 2026-11-07:

| Build | Licence | Why it does not fit |
|---|---|---|
| `@ffmpeg/core` 0.12.10 and `@ffmpeg/core-mt` 0.12.10 (ffmpeg.wasm), the plan's "~30 MB" | **GPL-2.0-or-later** (npm metadata): built with `--enable-gpl`, libx264 and libx265 | GPL: excluded by the brief. |
| openclaw/ffmpeg-wasm (FFmpeg n9.0.2, Emscripten 6.0.11) | LGPL-2.1-or-later FFmpeg, no `--enable-gpl` or `--enable-nonfree`; MIT wrapper | Built for Node. It has no prores_ks, no gif encoder and no palettegen/paletteuse. |
| libav.js 6.10.9 and its `@libav.js/variant-*` packages | LGPL-2.1 | No published variant has a ProRes or GIF encoder, or a mov muxer. Its `all` configuration lists `codec-prores` and `codec-gif`, but it is published only by a third party (`@uwx/libav.js-all`, a 6.0 nightly on FFmpeg 6.1.1, 128 MB) and has no CLI. |

**The build to make instead** has not been built: installing Emscripten in this session was refused. The proposal:
- **Source:** FFmpeg n7.1 (`https://ffmpeg.org/releases/ffmpeg-7.1.tar.xz`, with its `.asc` signature). This is the version the desktop runs, so prores_ks's output can match it.
- **Compiler:** Emscripten 3.1.74.
- **Licence:** LGPL-2.1-or-later. There is no `--enable-gpl`, `--enable-version3` or `--enable-nonfree`, and no external libraries.

```
emconfigure ./configure --target-os=none --arch=x86_32 --enable-cross-compile \
  --cc=emcc --cxx=em++ --ar=emar --ranlib=emranlib --nm=emnm \
  --disable-asm --disable-inline-asm --disable-x86asm --disable-autodetect --disable-network \
  --disable-doc --disable-debug --disable-everything \
  --disable-ffprobe --disable-ffplay --enable-ffmpeg \
  --enable-avcodec --enable-avformat --enable-avfilter --enable-swscale \
  --enable-protocol=file,pipe --enable-demuxer=rawvideo --enable-decoder=rawvideo \
  --enable-encoder=prores_ks,gif --enable-muxer=mov,gif \
  --enable-filter=scale,format,split,palettegen,paletteuse,setparams,null
```

The plan calls this `workers/ffmpegWasmWorker.js`. To fit it:
1. Link the `ffmpeg` program with `-sMODULARIZE -sEXPORT_ES6 -sALLOW_MEMORY_GROWTH -sMAXIMUM_MEMORY=4GB -lworkerfs.js`.
2. Run it in a worker on the same arguments `writers.FfmpegWriter._codec_args` builds for the desktop.
3. Feed it frames through a `SharedArrayBuffer` ring. The site is cross-origin isolated (`crossOriginIsolated` was true in the driver), so a frame need not be held whole.
4. Write the `.mov` to the origin-private file system.
5. Serve it from the assets bucket as a separate file, loaded only when a ProRes export starts. That is dynamic linking in the LGPL's sense.

With so few components it should be a few MB, not 30. When it exists, its exact build, source, sha256 and these flags go into `THIRD_PARTY_NOTICES.md`, marked to be confirmed by counsel. `PageEncoder`'s ProRes row becomes a browser route, and the hand-off notice goes.

**What needs the user:** permission to install Emscripten (emsdk) in WSL or in CI, and to download the FFmpeg source, so that build can be made and measured.

## How to rerun

```
PLEXORA_BENCH_HOME=<bundle home> PLEXORA_FFMPEG=<the desktop's ffmpeg> \
PLEXORA_PLAYWRIGHT_MODULES=<node_modules with playwright-core> \
  python -m pytest -q -p no:cacheprovider tests/test_browser_video.py
node tests/browser/video.mjs --out DIR --size 1280x720 --duration 4   # the timing run
python tests/browser/video_check.py DIR
```

Without an FFmpeg, the driver runs the website arm only. The wrapper then skips the movie checks and the comparisons.

Not tested here: Firefox and WebKit. MP4 and WebM there depend on their WebCodecs encoders, and the dialog says when one is missing. The GIF worker and the PNG frames need only a worker and the page's Python.
