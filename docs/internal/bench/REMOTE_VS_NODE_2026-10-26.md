# Direct data access versus remote streaming: a benchmark of Plexora on HMS O2

Date: 2026-10-26. Status: complete. Experiments A–D are 8 paired blocks; Experiment E
(within-file scaling over channels) is a smaller series, reported in §6.6.

Claims are tagged as in the technical report:
- **Measured**: a number from this campaign's raw rows.
- **Design**: how the software is built, read from the source.
- **Proposed**: not done here.

Every number below can be regenerated by `tools/bench_remote/analyze.py` from the files
in this folder (§9).

## 1. Question

A large image lives on a cluster's shared storage. A researcher views it from a
laptop. Plexora offers two ways to do this:

- **Data node (direct access).** `plexora node serve` runs on an O2 compute node
  next to the file. It reads, decodes and encodes tiles there, and sends encoded
  tiles through an SSH tunnel; the browser fetches them from the node directly.
- **SFTP streaming (files only).** Plexora runs on the laptop and reads the file's
  raw bytes over one SFTP channel to O2's transfer node, where nothing may run.
  Tiles are decoded and encoded on the laptop, through an on-disk chunk cache.

We measured connection set-up, cold and warm starts, data transferred, scripted
navigation to an objective full-resolution end point, and scaling with the
number of channels shown. Same laptop, same network, same file, same software.

## 2. Architecture review and feasibility (Design)

| | Data node (N) | SFTP streaming (S) |
|---|---|---|
| Where bytes are read | O2 compute node (NFS client of `/n/scratch`) | O2 transfer node (`sftp-server`), then over the internet |
| What crosses the network | encoded tiles (16-bit PNG in HD mode, about 2 MB per 1024² tile) | raw HDF5 chunk bytes, 64–255 KiB SFTP reads, up to 64 in flight |
| Where decode and encode happen | compute node | laptop |
| Imaris chunk index (`.ims_index`) | built once on the node, kept | not built (remote files); HDF5 B-tree walked over SFTP |
| Background work (contrast windows, z read-ahead) | on the node, beside the file | on the laptop, over the same SFTP channel as the visible tiles |
| Browser caching of tiles | none: tiles come in batched POST requests | yes: tiles are cacheable GETs |
| Persistent caches | node derived files (`.ims_index`, quantization) | on-disk chunk cache (`.remote_cache`, 10 GiB) |

**The dataset** (Measured). `normal_TLS_13.ims`:
- 687,147,223,614 bytes (640 GB);
- 51 channels, 256 z-planes, 5668 × 8432 px, uint16, 7 resolution levels;
- HDF5 chunks of 8 × 256 × 256 at levels 0–1 and 32 × 128 × 128 at levels 2–5.

So a level-0 tile at one plane touches chunks eight planes deep, and a level-2
tile touches chunks 32 planes deep.

**Fairness checks** (Measured):
- **Same pixels.** The same tile fetched through each arm is byte-identical: equal SHA-256 for 16-bit HD and for 8-bit WebP.
- **Same code.** The O2 checkout ran commit 8b01f6ae, and the laptop that commit plus benchmark-only instrumentation (counters, a gated cache-flush route; §8). No rendering or tile code differs between the arms.
- **Same viewer path.** HD mode is on in both arms. In arm N every node tile was fetched by the browser directly from the node (origin `node-direct`).

## 3. Set-up (Measured)

**Laptop.**
- Apple M2 Pro (10 cores), 32 GB, macOS 26.6, wired Ethernet.
- Chrome 131, headless, GPU rendering via ANGLE/Metal. A software renderer is refused by the harness.
- A 1440 × 900 window at DPR 1.

**Data node.**
- One SLURM job on `short` (10 CPUs, 32 GB, 10 h), on a shared Intel Xeon Platinum 8468 host (96 cores, 1 TB).
- The node process runs inside the job's cgroup.

**Network.** From the laptop:
- median TCP connect time 83 ms to the login node and 85 ms to the transfer node (ranges 22–100 ms and 27–160 ms);
- SFTP streaming with Plexora's own client: 31.6 MB/s for a 256 MB contiguous read;
- a single small SFTP read: 47 ms.

**CPU calibration.** The same seeded 1024² uint16 tile, encoded on both hosts (median of 30):

| Encoding | Laptop | Node |
|---|---|---|
| 16-bit PNG (HD) | 1.9 ms | 2.6 ms |
| 8-bit WebP | 50 ms | 62 ms |

The laptop is about 1.3× faster per core, so CPU speed does not favour the node arm.

## 4. Protocol

**Unit of replication: the block.**
- A block is one paired run of both arms on one waypoint set.
- There were 8 blocks, the arm order alternating ABBA from a seeded coin flip.
- Waypoints came from a survey picture of the tissue: 6 sets, blocks alternating between planes z0 = 96 and z0 = 160.

**Cache states** (cleared only for our own processes and our own file; nothing system-wide):

| State | Data node | SFTP |
|---|---|---|
| C0, first-ever open (3 N reps, 2 S reps) | node derived files deleted; the file's pages dropped from the compute node's page cache (`posix_fadvise` DONTNEED, verified to 0 bytes with `fincore`); new node, new laptop Plexora, new project | chunk cache deleted; new Plexora and SFTP login; new project |
| C1, cold | page cache dropped as above; new node process (empty tile and chunk caches); new laptop Plexora; derived files kept | in-memory caches emptied and the on-disk chunk cache returned to its post-import contents (the HDF5 metadata a returning user has); see §8 |
| C2, warm | the same processes and the same Chrome, immediately after C1 | same |

**The tour** (identical in both arms):
1. open at plane z0, fit to the window;
2. turn on 3 channels;
3. zoom to level 2 at waypoint a;
4. zoom to level 0 at a;
5. pan to a distant waypoint b at level 0;
6. go home;
7. revisit a;
8. jump to an unvisited waypoint c at level 0;
9. step z + 1, then z + 8, then z + 50;
10. an animated zoom, then an animated pan;
11. enter the 3-D view.

Each instantaneous step is timed from the page clock; the animated steps run OpenSeadragon's own spring animations.

**Full-resolution end point.** A step is complete only when all of these hold:
- every visible channel is fully loaded;
- it draws the finest pyramid level OpenSeadragon selects for that view (its own `minPixelRatio` test);
- it comes from an HD source;
- the view token on screen matches the requested plane;
- all of the above have held for two consecutive polls, at least two redraws after the step began.

A low-resolution preview never counts. A step that is not full within 120 s is right-censored at 120 s; the open step's cap is 300 s.

**Bytes.**
- **Wire:** cumulative socket bytes of the SSH process carrying the arm's traffic (`nettop`).
- **Delivered to the browser:** per-request `encodedDataLength`, from Chrome DevTools.
- **Read on the far side:** for N, `/proc/<pid>/io` of the node; for S, the SFTP client's counters (READ replies).

**Statistics.**
- Per metric: median, IQR, p95, and a percentile-bootstrap 95% CI of the median.
- Paired effect: the geometric-mean ratio S/N over blocks, with a paired-bootstrap 95% CI (10,000 resamples) and a Wilcoxon signed-rank p.
- Four pre-specified primary endpoints: open (C1), the per-block median navigation step (C1), wire bytes per cold tour, and p95 frame interval during the animated pan. Their p-values are Holm-adjusted.
- Completion rates carry Wilson 95% intervals. Censored S values make the ratios lower bounds.

## 5. Confounders and how each was handled

| Confounder | Handling |
|---|---|
| CPU differs between hosts | calibrated (§3); the laptop is faster, which favours S |
| Node allocation size | the node matched the laptop (10 cores, 32 GB) |
| Shared compute host | the job's cgroup limits the node to its allocation; host load (about 40 of 96 cores in use) recorded per session |
| NFS server (VAST) cache | uncontrolled, affects both arms; fresh waypoints and alternating planes per block |
| Transfer node page cache | uncontrolled (nothing may run there), favours S on re-reads; same mitigation |
| The S chunk cache persists across sessions by design | reset to its post-import state before each cold block |
| Browser cache | a new Chrome profile per block (C1); kept within the block (C2) |
| Saved view state | the viewer's view-state and channel-list writes were answered in the browser and never reached the server; the project's saved rows were cleared before each pass |
| Link variability | round-trip times recorded per block; ABBA ordering |
| Laptop background load | load and any test run recorded per row (other users' sessions ran on this machine during the campaign) |
| Routing origin | asserted from the tile URLs: N tiles were `node-direct` |

## 6. Results

### 6.1 Connection set-up (Experiment A, Measured)

**Data node.** Starting the node inside the running job took a median of 7.7 s (6.8–14.7 s, 8 cold blocks), from start to the node answering through the tunnel. In C0, which also includes the SSH set-up to the job, it took 23 s (21.6–23.3 s, 3 reps).

**SFTP.** A fresh SFTP login to the transfer node took 12 s (2 C0 reps). In the paired blocks the SFTP session was opened once and reused (§8).

### 6.2 First-ever open (C0, Measured)

| Arm | Import (s) | First full-resolution view (s) | Bytes before that view |
|---|---|---|---|
| Data node (3 reps) | 11.9 (11.4–20.0) | 2.3 (1.5–7.6) | 8–15 MB through the tunnel |
| SFTP (2 reps) | 1,156 (1,111–1,201) | 55 (55–56) | 3.70 GB in about 28,800 SFTP reads |

Over SFTP, h5py walks the HDF5 metadata of a 51-channel, 7-level file as tens of thousands of small, scattered reads, each costing a round trip. The SFTP client's summed request wait was 7,600–7,800 s for those 28,800 reads. On the node the same walk is local, and the `.ims_index` makes later opens skip it.

### 6.4 Interaction (Experiment D, Measured)

Navigation steps at full resolution (11 per tour, 88 per arm per pass):

| Pass | Arm | by 2 s | by 10 s | by 60 s | by 120 s (95% CI) |
|---|---|---|---|---|---|
| C1 | Data node | 61% | 100% | 100% | 100% (96–100%) |
| C1 | SFTP | 27% | 30% | 67% | 87.5% (79–93%) |
| C2 | Data node | 76% | 100% | 100% | 100% (96–100%) |
| C2 | SFTP | 89% | 93% | 99% | 100% (96–100%) |

**Frame pacing did not differ.** The p95 frame interval during the animated pan was 9.2 ms in both arms (about 108 Hz display). Dropped frames per animated step were 0–9 in either arm, with no systematic difference. The remote arm delays *when* full resolution arrives; it does not make the view stutter.

### 6.5 Data transfer (Experiment C, Measured; GB per tour, median [IQR])

| Pass | Arm | Into the laptop (wire) | Delivered to the browser as tiles | Read from the file on the far side |
|---|---|---|---|---|
| C1 | Data node | 0.55 [0.52–0.56] | 0.54 [0.51–0.55] | 7.34 [6.89–7.56] |
| C1 | SFTP | 15.4 [14.9–16.6] | 0.75 [0.60–0.85] | 15.5 [14.9–16.6] |
| C2 | Data node | 0.56 [0.55–0.59] | 0.42 [0.38–0.42] | 0.95 [0.82–1.05] |
| C2 | SFTP | 1.71 [1.24–2.43] | 0.71 [0.65–0.78] | 1.73 [1.23–2.43] |

**Data node.**
- Over the wire it sent almost exactly what the browser drew: wire ≈ tiles, about 2% framing overhead.
- To produce those tiles it read 7.3 GB from the file locally (6.1 GB from storage, per `/proc` `read_bytes`), using 51 s of node CPU per cold tour.
- Most of that is the background contrast statistics and plane read-ahead, which run beside the data. The node needed 1.6 s of CPU in the warm pass.

**SFTP.**
- The laptop pulled 15.4 GB per cold tour: 20× the bytes of the tiles it drew, and 2.4% of the 640 GB file.
- The amplification comes from three things:
  - 8- and 32-plane-deep chunks, read whole for a single plane;
  - the same background statistics and read-ahead, now competing for one SFTP channel;
  - a 4 GiB decoded-chunk cache that the statistics scan fills, evicting chunks of the visible view.
- A cold tour took 517 s of wall time over SFTP, against 24 s on the node; a warm tour took 26 s against 16 s.

### 6.6 Within-file scaling (Experiment E, Measured)

Each run was cold (C1): open, show the first k channels (k = 1, 3 or 5), zoom to level 2, jump to an unvisited level-0 region, then step z + 8. There were 2 runs per arm and channel count, on fresh waypoint sets at plane 128, which the blocks did not use. Medians of 2:

| Channels | Data node: L2 zoom / L0 jump / z + 8 (s) | SFTP: L2 zoom / L0 jump / z + 8 (s) | Bytes into the laptop per run, node / SFTP (GB) |
|---|---|---|---|
| 1 | 0.93 / 0.60 / 0.75 | 27.2 / 20.0 / 19.2 | 0.05 / 3.4 |
| 3 | 2.51 / 1.70 / 2.30 | >120 (2 of 2 censored) / 105 (1 censored) / 63.5 | 0.15 / 9.2 |
| 5 | 4.37 / 1.92 / 3.28 | >120 (2 of 2) / >120 (2 of 2) / 101 (1 censored) | 0.23 / 10.8 (capped by the timeouts) |

**Data node.** Its time and bytes grew roughly in proportion to the channels shown, and every step stayed under 5 s.

**SFTP.** Already 26–33× slower with one channel, it stopped reaching full resolution within 2 minutes from three channels onward. Each added channel adds its own chunk reads over the same SFTP channel, and the 4 GiB decoded-chunk cache cannot hold several channels' 8- and 32-plane chunks at once. This is a small series (n = 2 per cell) and is reported descriptively.

### 6.7 Where each arm wins

**The data node wins every cold, first-visit step** by 10–54×, and the first-ever open by about 30× (0.6 min against 20 min). It also moves 29× fewer bytes and keeps 100% of steps under 10 s.

**SFTP wins two things:**
- a plane step inside the chunk it has just decoded (z + 1: 0.56 s against 2.3 s);
- almost every warm revisit, at 0.16–0.5 s against 1–2 s. Its tiles are made and cached on the laptop, while the node re-sends about 2 MB per 16-bit HD tile each time: batched POSTs are not cached by the browser.

The 3-D view stays faster on the node even warm (0.15 s against 0.53 s).

## 7. Limitations

- **Scope.** One laptop, one home connection (about 85 ms round trip, 32 MB/s for SFTP), one cluster, one file and one commit. Effect sizes will move with round-trip time and bandwidth: SFTP's metadata walk scales with round-trip time, the node's tile transfer with bandwidth. No dataset-size ladder: by the user's choice only this file was used; Experiment E varies channels within it.
- **Uncontrolled server-side caches.** The NFS server's cache and the transfer node's page cache could not be controlled. Fresh waypoints and alternating planes limit re-reads; any residual favours SFTP.
- **Cold state for SFTP is reconstructed, not a restart.** To avoid a Duo push per block, the SFTP arm kept one Plexora process and its SFTP session across blocks. Before each cold block its in-memory caches were emptied and its on-disk cache returned to the post-import snapshot (§8). Contrast windows computed in earlier blocks stayed known, as they also did for the node (its quantization files persist). This can only make SFTP's cold numbers better than a true restart.
- **Censoring.** Steps were capped at 120 s, and ratios involving censored SFTP values are lower bounds.
- **HD only.** The comparison used HD (16-bit) tiles, the default for both arms. Fast (8-bit WebP) tiles would cut the node's bytes about 4.7× (450 KB against 2.1 MB per tile in calibration) and leave SFTP's raw-byte reads unchanged. Not measured here (Proposed).
- **Allocation size.** Only the matched 10-core, 32 GB node was measured. The node was never the bottleneck (51 s of CPU over a 24 s tour), so a larger allocation is not expected to change the ordering (Proposed).
- **Shared laptop.** Other sessions used the laptop throughout: another session's pytest process was running in 30 of 32 passes, and the 1-minute load average at the start of an arm was a median of 7.6 (N) and 11.1 (S, range 5.9–32.7) on 10 cores. This could slow SFTP's laptop-side decoding. It is not the dominant factor: a cold SFTP tour moved 15.4 GB, which at the measured 31.6 MB/s takes 488 s, against a measured 517 s, so that arm is limited by bandwidth. No block was excluded.
- **One block's SFTP arm failed in the harness** (a page evaluation returned nothing). It was rerun at the end in the same session and the rerun is used; every row is kept in `runs.jsonl`.

## 8. Deviations from the plan

- **Partition.** The node ran in a `short` job rather than `interactive`, which refuses `sbatch`. Both partitions draw on the same node pool.
- **No new logins mid-run.** O2 runs Duo on every new session on the login node. The harness therefore ran all cluster commands down one long-lived shell on the compute node, started the node from there inside the job's cgroup, and added the tunnel as a forward on an existing SSH master.
- **One SFTP Plexora for the run.** For the same reason the SFTP arm kept one Plexora process. It returned to the cold state through a new route, `POST /volume/_bench/flush`. The route answers 404 unless `PLEXORA_BENCH_FLUSH=1`, and empties the level, decoded-chunk, tile and block caches. It also drops on-disk chunk-cache entries that the post-import snapshot does not list.
- **Secondary cells not run.** Fast tiles, proxied routing and the 16-core, 128 GB node were planned as secondary cells; see Limitations.
- **Fewer channels in E.** The scaling series used 1, 3 and 5 channels, because the viewer shows at most 5 at once.
