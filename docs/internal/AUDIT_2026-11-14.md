# Plexora codebase audit, November 2026

Branch `audit/2026-11` (worktree `C:\pxaudit`), based on main at `292c027a`.
Nothing is merged or pushed. The branch is for review.

## 1. Summary

**Method.**
- **Find.** 55 finder agents each read one slice of the code, applying the seven lenses of the request: functional, state, multi-node, data integrity, performance, plugins/UI, concurrency/errors. 48 slices were groups of files; 7 followed a flow across files (project lifecycle, user-authored state, table row identity, remote nodes, the website, coordinates and units, hot paths). A completeness critic then named the most important unread code, and 8 more finders covered it.
- **Verify.** One verifier per lead tried first to refute it. When it could not, it proved the lead with a regression test that fails on the unfixed code.
- **Fix.** Each confirmed bug went to a fixer, a separate reviewer, and at most one revision round. Groups that touch the same file were scheduled never to run at once.

**Outcome.**

| | Critical | High | Medium | Low | Total |
|---|---|---|---|---|---|
| Confirmed and fixed by the audit (each with a regression test) | 27 | 49 | 80 | 1 | **157** |
| Confirmed, held for a decision, then fixed on review (§5) | 1 | 1 | 1 | 0 | **3** |
| Leads found but not verified (caps, see §7) | 1 | 11 | 110 | 117 | **239** |

- **Verdicts.** All 160 verified leads were confirmed: 158 by a failing test and 2 by trace only (`ep-desktop-2` and `r2-website-boot-store-3`). No verified lead was refuted; the finders had already set aside 656 suspicions as "checked fine" (§8). All 160 are now fixed.
- **Tests.** All 158 new test files failed on the unfixed code: 337 failed, 58 passed in one run. They all pass on this branch. The two that were strict xfail until §5's fixes landed now pass too.
- **Categories of the fixed bugs.** Data integrity 55, state 28, concurrency/errors 18, functional 18, performance 17, multi-node 14, plugins/UI 7.

**What the critical ones were**, in short:
- **Stale data served as current:**
  - tiles kept for a year at addresses with no content version (S3);
  - a deleted and re-created project serving the old one (S1, flow-project-1);
  - centroid tiles that ignore the read spec (S6);
  - a remote chunk cache that never revalidates (S11);
  - a boundary mask reused across registrations (io-formats-2).
- **Wrong pixels or cells:**
  - SourceImage reading the wrong pyramid levels (io-image-1);
  - a ZVI/compound-file race (io-formats-1);
  - an in-memory mask pyramid that averaged cell ids (cl-website-1);
  - two notebook kernels sharing one node name (N4);
  - a coarse 3-D level evicted to zeros (io-volume-1).
- **User work lost or overwritten:**
  - a failed saved-state read at boot writing defaults over saved gates (cl-lifecycle-1);
  - closing an AI QC session dropping hand-drawn QC regions (pg-qc-b-1);
  - a refused table swap overwriting the table (sc-import-1).
- **Security:** a `.plexora` file name executed as PowerShell code during relink on Windows (sc-bundles-1).
- **Units:** a figure capture's pixel size in nm or mm read as microns, so scale bars were 1000x wrong (pg-fig-workspace-4).

**What is not covered.**
- **Unverified leads.** 239 leads were found but not verified, because of the caps: 8 promoted per finder, 135 verifications in round 1 and 25 in round 2. They are listed in §7, and the high and critical ones are named in §6. Most are medium or low, but 11 are high and 1 is critical.
- **Unread code.** Each finder's ledger of what it did not read is in §8.
- **Not run here:**
  - the Rust desktop shell during the audit (`cargo test` was run afterwards for ep-desktop-2, §5: 31 passed);
  - the relay and backend TypeScript test suites;
  - real ssh, O2, cloud buckets and the public relay.
- **No real browser.** Client fixes were proven with the node:vm probes (`tests/js/*_probe.mjs`), not in Chrome.

## 2. How to read the entries

- **Severity:**
  - Critical: silent wrong data, data loss or a wrong scientific result.
  - High: a crash, a hang, or a broken workflow with no workaround.
  - Medium: wrong behaviour with a workaround, a leak, or a large avoidable cost.
  - Low: minor.
- **Verdict:**
  - "Confirmed by test": the named test failed on `292c027a` for the stated reason.
  - "Confirmed by trace": the bug was proven by reading the code, without a deterministic test. A second, independent skeptic checked the trace and did not refute it.
- **File and line references** in "Root cause" point at the code *before* the fix (`292c027a`).
- **Resolution** names the commit(s) on this branch. A commit that fixes several bugs lists all of them in its subject (`(audit A, B)`), and its body has a paragraph per bug with the root cause, the fix and the test.

## 5. Held for a decision, then fixed on review

The audit held these three back, because their fixes went past what it would land on its own: a node API change, a change to how a remote viewer is reached, and a Rust change that was not run here. Their regression tests were committed as `xfail(strict=True)`. On review, the decision was to fix all three. Each entry keeps its original root cause and proposal, followed by what was done.

- **nr-node-1** — A node table resource holds one read spec, so projects sharing a cohort table on a node read each other's cells  
  *critical, Data integrity; deployments: all; verdict: confirmed by test.*  
  **Root cause:** The node keeps one spec and one provider per resource, and the reads never say which spec they mean. plexora/server/node/resources.py:936-994 `load_table` replaces `resource.provider` (976), `resource.spec` (977) and `resource.project` (978), and bumps `generation` (979). The resource id comes from the file path alone (plexora/nodes.py:257-286 `resource_id_for`, used by `share_path` at nodes.py:331).  
  **Trigger:** One multi-image .h5ad or SpatialData table on a data node is imported for two or more slides (subset image_id=X per project), and a second loader loads another slide's project while the first one stays open.  
  **Components:** `plexora/server/node/api.py`, `plexora/server/node/resources.py`, `plexora/server/providers/http.py`, `plexora/server/providers/node.py`  
  **Status:** held for a decision (a node API change); fixed on review. **Proposed fix (as held):** Root fix, on the node: keep the loaded providers per spec, not one per resource. In resources.py, key a small LRU of (provider, project) on the Resource by a stable hash of the node-side DataSpec dict. `load_table` returns that spec key. Read and op routes in api.py take an optional `spec=<key>` query parameter and resolve the provider and Dataset from it. If the key is missing or has been evicted, they answer a typed "reload" error.  
  **Resolution:** b8a95a0a, as proposed, with one change: the key hashes the spec as the primary *sends* it (`http.spec_key`). Both ends can then compute it, so an operation that has only a project, not a loaded provider, can still name its spec.
  - The node keeps up to 4 loaded specs per table (`LOADED_SPECS`).
  - Reads and operations send `?spec=<key>`.
  - A spec the node does not hold is a 409 with `X-Plexora-Spec-Missing` (`SpecNotLoaded`). The primary then loads the spec and repeats the request once; a write is safe to repeat because the node refuses before running it.
  - There is no `API_VERSION` change. An older node ignores the parameter, and an older primary gets the spec loaded last, as before.
  
  **Test:** `tests/test_node_table_two_projects_one_resource.py`, now 7 tests, all of which fail on the old code. The xfail mark is removed.
