# Telemetry

Plexora's usage telemetry is optional, anonymous, allowlisted field by field,
and never required: Plexora is fully functional air-gapped, and no viewer,
plugin, analysis, import, rendering, remote-node, notebook, desktop or agent
feature depends on the telemetry service. This page is for people who want to
know exactly what happens, and for developers adding a count.

## Modes and off switches

| Mode | What is sent |
|---|---|
| `off` | Nothing. The local queue is emptied. |
| `anonymous` (default) | Counts and timing bands: features, plugins, capabilities, tile and render timings, error fingerprints, coarse dataset shape. |
| `diagnostics` | The same, plus GPU family and exact channel counts. Still no content. |

Resolved highest first: the test suite (`off`); `DO_NOT_TRACK` set to anything
but `0` (`off`); `PLEXORA_TELEMETRY=off|anonymous|diagnostics`; a pause the
service set for this version; the Settings page / `plexora telemetry
on|diagnostics|off` (stored as `telemetry.mode` in settings.json); the default.
The service can also cap a version at `anonymous`, which only ever lowers.

`plexora telemetry status` says which rule is in force and why;
`plexora telemetry preview` prints the next upload exactly as it would be sent;
`plexora telemetry reset` replaces the random install id and drops what was
queued under the old one; `plexora telemetry send` uploads now.

## What is never sent

File, project, dataset, sample, marker, gene or column names; cell data or
coordinates; paths, URLs or query strings; usernames, hostnames, IP addresses
or hardware ids; agent prompts or capability arguments; exception messages or
stack traces; licence tokens or secrets. There is no free-text field anywhere
in the schema: every value is an enum member, a band label, a bounded number,
a boolean, a nine-bin histogram, or a code identifier / hex digest matching a
strict pattern. A second check (`plexora/telemetry/redact.py`) drops any event
that still contains a path, URL, address, long hex run or one of this user's
own names. `tests/test_telemetry_privacy.py` runs a session full of personal
strings and asserts none of them reaches the upload.

Third-party plugin, capability and route names are reported as
`ext:<8 hex of sha256(name)>`: the name is theirs to publish, not ours.

## How it flows

```
browser tab ──POST /telemetry/ingest──▶ local Plexora server ──▶ queue.sqlite ──▶ uploader ──HTTPS──▶ Worker (Cloudflare)
 (aggregate,          every 5 min,        (validates rows,         (hourly        (one thread,
  no URLs kept)       on hide/unload)      folds into the hour)     windows)       5 s timeouts)
data node ── cumulative counts on /node/v1/hello ──▶ primary folds the delta (nodes never upload)
```

- **The tab is a producer only** (`services/telemetry.js`,
  `performanceTelemetry.js`, `errors.js`). It never contacts the service.
  Tile requests are classified by their path's shape into `{path, kind}`
  and the URL is dropped at once; `Server-Timing` on tiles carries the
  server's own read/LUT/encode phases back to it.
- **The server aggregates before it stores** (`plexora/telemetry/client.py`).
  A request thread does an in-memory increment; a writer thread upserts into
  `<data root>/.telemetry/queue.sqlite` every 30 s (rollback journal, not WAL,
  so it works on NFS). The queue is capped at 10 MB and 30 days.
- **One uploader thread** (`uploader.py`) sends closed hourly windows about
  once an hour, gzipped, with an install token obtained by exchanging the
  random install id at `/v1/telemetry/register`. No secret ships with the
  client. Failures back off (1 min to 24 h) and persist; there is never a
  connectivity probe. Uploads go to `config.DEFAULT_ENDPOINT`
  (`https://analytics.plexoraapp.com`) unless `PLEXORA_TELEMETRY_ENDPOINT`
  names another; the test suite empties the default, and release smoke boots
  set `DO_NOT_TRACK`, so neither reaches it.
- **The service** (`backend/`) validates against the same allowlist
  (`backend/vectors/plexora-vectors.json`, generated by
  `scripts/sync_telemetry_vectors.py`), stores one compact row per upload in
  D1, rolls up daily, archives each day to R2 as a verified `.jsonl.gz`
  before purging it, and degrades ingestion before it reaches the Cloudflare
  free-tier limits. A client newer than the deployed service is never
  refused for it: what the service's allowlist does not know is dropped and
  counted (`unknown` in its answer), and the rest is kept. See
  `backend/README.md`.
- **A refusal is visible.** If the service will not register an install,
  `plexora telemetry status`, `plexora telemetry send` and Settings › Usage
  data say so, with the service's status and reason, instead of "never sent".

## Adding a count

1. Add the event, key or field to `plexora/telemetry/schema.py` with the
   tightest type that works and the least mode it belongs to. A new string
   field is almost always an `Enum`.
2. Call `telemetry.count/observe/emit` (Python) or
   `PlexoraTelemetry.count/observe/feature` (browser), or from a plugin
   `ctx.telemetry.feature(name)` for a key in `FEATURE_KEYS`.
3. Run `python scripts/sync_telemetry_vectors.py` and commit the regenerated
   `backend/vectors/` and `backend/test/fixtures/` files; the Worker's tests
   and `tests/test_telemetry_schema.py` fail on drift.
4. Nothing else. The service only counts what its deployed allowlist knows,
   so it is redeployed whenever the vectors change: by
   `scripts/release.py` before a version is built (`bump`, `all --release`,
   `ci`; `python scripts/release.py telemetry` does it alone), and by
   `backend.yml` on the push to `main`. Until then the new value is dropped
   and counted as `unknown`, never refused. `GET /healthz` names the live
   allowlist (`vectors`, a fingerprint the vectors file also carries).

Never count on a request thread anything but an in-memory increment: no
SQLite, no JSON, no network, no datasource load.

## Analytics and licensing are separate

The client block reserves optional `license_account_id`, `license_id_hash`,
`seat_id`, `machine_id_hash` and `activation_id` fields, and the service has a
reserved `license_summary` table and nullable licence columns on `installs`, so
that a future licensing service can report aggregate counts without a
redesign. None of them is set by this client. Licence enforcement, activation
and seat management do not belong in telemetry and will not be built on it: a
licence check must work when telemetry is off, and turning telemetry off must
never affect a licence. The install token is not a licence of any kind.
